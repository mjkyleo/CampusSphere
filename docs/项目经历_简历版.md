## 五、Bullet 备选池（按主线组织，可自由组合）

> 主线建议：**并发一致性 → 实时链路 → AI 工程化 → 安全 → 可观测**。每条已按「矛盾 → 解法 → 兜底 → 量化」三层 + 末端数字写就，可直接取用。

### A. 并发与数据一致性

**A1｜条件 UPDATE 原子抢占 + 部分唯一索引**
针对多买家同时对同一在售物品发起交易的"一物双卖"竞态，设计「条件 UPDATE 原子抢占（CAS）」，把"读状态 → 判断 → 写状态"合并为单条 `UPDATE items SET status=RESERVED WHERE id=? AND status=ON_SALE` 并以 `rowcount==1` 判定胜出，配套活跃交易会话的部分唯一索引（`sqlite_where` + `postgresql_where` 双方言声明，仅约束 `status IN (0,1)` 活跃态）+ 同事务 `IntegrityError` 回滚 + `TRANSITIONS` 状态机迁移白名单（允许 RESERVED 回退防卡死），实现并发冲突由脏写收敛为确定性 409，判定路径由 3 次 RTT 压缩为 1 条 SQL。

**A2｜缓存三件套**
针对列表接口高频回源与缓存集中过期的雪崩风险，设计"空值哨兵 + TTL 抖动 + 版本化命名空间"缓存层，采用 `NULL_SENTINEL` 空结果短缓存（10s）防穿透、TTL 叠加 [0,15] 随机抖动防雪崩、命名空间版本号 `INCR` 使旧键自然失效（无需 SCAN），配套参数稳定哈希（sha256 前 16 位）作键，实现缓存失效 O(1) 且与内存降级模式兼容。

### B. 实时链路

**B1｜窗口函数去 N+1**
针对会话列表需同时返回末条消息与未读数而产生的每会话 3 次查询（O(3N+1)），设计"窗口函数 + 批量聚合"合并查询，采用 `row_number() over(partition_by=conversation_id order_by=created_at desc)` 取 `rn==1` 得末条消息、`GROUP BY` 一次取全部会话未读、批量 `IN` 查对端资料，配套跨实例推送（本地直发 + Redis Pub/Sub 广播），实现固定 4 条 SQL，查询量与会话数解耦。

**B2｜ZSet LocalSeq 精准断线补偿**
针对用时间戳做增量游标"同刻度丢消息 / 放宽为 `>=` 又重复推"的两难，设计「Redis ZSet 单调序号」替代时间戳，采用 `INCR` 分配跨实例唯一序号、`ZRANGEBYSCORE (N +inf]` 开区间精确补发，配套 `ZREMRANGEBYRANK` 滚动裁剪保留最近 500 条、单次补发上限 200 条、无 Redis 时退化为进程内序号表，实现重连补发不重不漏且连接不断。

**B3｜前端 401 并发合并刷新**
针对 access token 过期时多请求并发 401 会重复触发刷新并互相覆盖 token 的问题，设计"单例刷新 Promise"机制，采用 `isRefreshing` 标志 + `refreshPromise` 共享同一刷新请求、成功后自动重放原请求，配套 `softAuth` 模式让未读数等非关键请求刷新失败时降级返回而非强制登出，实现并发 401 只触发一次刷新，避免抖动导致的误登出。

### C. AI 工程化（Agent 岗重点）

**C1｜三层接入：直调 + 护栏 + 降级**
针对外部大模型存在超时、配额、输出格式抖动三类不确定性，设计"直调 + 护栏 + 降级"三层接入（开关 → 能力级 → 模型链+熔断，现已真实落地），采用 `httpx.AsyncClient(timeout=30)` 异步直调 OpenAI 兼容 /chat/completions（兼容 DeepSeek/Qwen/Kimi/GLM/Ollama，不引 SDK，减依赖树）、API Key 仅存后端（环境变量优先于配置中心），配套 `app_config` 实时功能开关与无 Key 降级，实现未配置 Key 时前端按 `/api/ai/status` 自动隐藏 AI 入口、主流程零阻塞。

**C2｜Prompt 工程与输出容错**
针对模型输出常带 markdown 代码围栏或超出枚举导致解析崩溃，设计"结构约束 + 枚举收敛 + 兜底归类"解析层，采用 `response_format={"type":"json_object"}` 约束输出形态、按任务分档配置 temperature（创作 0.8 / 文案 0.7 / 摘要 0.4 / 分类 0.1）、校验结果落在 9 类枚举内否则归入"其他"，配套输入长度护栏（正文 3000 字 / 单条评价 500 字 / 评价上限 50 条），实现模型输出抖动不再向用户透传错误。

### D. 安全

**D1｜管理端存在性隐藏**
针对 `/api/admin/*` 被扫描探测的风险，设计「HMAC 时间槽网关令牌」，采用 `HMAC-SHA256(gateway_key|SECRET_KEY, "admin-gateway:{时间槽}")` 派生无状态短时令牌（3600s 轮换、校验同时接受当前槽与前一槽以覆盖时钟偏差），未携带有效令牌一律返回 **404 而非 403**，配套 Scope 偏序 RBAC（read⊂write⊂admin）与 User/AdminUser 双身份体系，实现管理端可达性对外不可见。

**D2｜自研滑块四重反刷**
针对注册验证码被脚本刷取轰炸校园邮箱，设计服务端渲染的行为式滑块验证，采用 Pillow 生成 **PNG 位图**（SVG 明文会泄露缺口坐标）、缺口横坐标**只存 Redis 不下发**（响应仅含纵坐标）、三重判定（位置容差 6px + 拖动耗时 ≥80ms + 轨迹非匀速且 ≥6 个采样点），配套有限次令牌（3 次失败即作废）+ 一次性发码票据 + `asyncio.to_thread` 隔离 CPU 密集渲染，实现刷码路径被票据一次性与尝试上限双重封死。

**D3｜双 Token 与分级限流**
针对令牌泄露与暴力破解风险，设计双 Token + jti 黑名单体系，采用 access 15min / refresh 7d、注销时把 `jti` 写入 Redis 黑名单且 TTL 设为**剩余有效期**（避免黑名单无限膨胀），配套全局限流 120 次/分与认证端点**独立严格**限流 10 次/分、验证码 TTL 300s 且最大校验 5 次，实现认证面与业务面限流隔离。

### E. 可观测与治理

**E1｜trace_id 穿透到 SQL**
针对线上慢查询无法反查所属请求的问题，设计「SQL 注释染色」链路追踪，采用 dialect 级 `do_execute` **监听器接管执行**注入 `/* trace_id=xxx */`（注释对数据库透明、不改执行计划，却能原样出现在慢查询日志与 pg_stat_statements），配套对客户端 `X-Request-ID` 做白名单正则收敛与 64 字符限长以**防止注释闭合型 SQL 注入**，实现 Nginx → 应用 → 慢 SQL 串行可追溯。

**E2｜六层配置 + 原地热更新**
针对"一所学校一套代码"的重复部署成本与改配置即发版的低效，设计六层配置优先级（代码默认值 → `school.yaml` → `.env` → DB `app_config` → 运行时热更新 → 前端兜底），敏感字段 `.env` 优先于 yaml（防仓库占位值顶掉生产密钥），采用 Redis Pub/Sub 广播 `config:reload` 触发**原地 setattr 刷新**（避免导入期绑定的 `settings` 引用静默失效）+ 监听器异常自愈（30s 重试），配套生产启动 fail-fast 校验（弱密码/默认密钥直接拒绝上线），实现改配置即上线、无需发版。

**E3｜零外部依赖的可测基建**
针对外部中间件导致的测试环境搭建成本，设计"降级优先"的基础设施与测试体系，采用临时 SQLite（每用例 `drop_all + create_all` 重建）+ 强制 Redis 连接失败走内存兜底 + MinIO/Meili 复用生产降级路径，配套自研 `create_async` 解决 factory_boy 与异步 SQLAlchemy 不兼容问题，实现 **342 个后端用例 + 25 个 E2E 用例在无网络、无 Redis、无对象存储环境下全量跑通**。

## 八、面试展开：每条 bullet 的追问预案

| Bullet | 高频追问 | 你的应答要点（一句话） |
| --- | --- | --- |
| A1 CAS | 为什么不用分布式锁 / Redis 锁？ | CAS 把一致性交给数据库单行原子性，无额外组件、无锁超时与续期问题；唯一索引作二次兜底，成本远低于引入 Redlock |
| A1 CAS | 失败为什么不重试？ | 抢购场景重试只会放大冲突；直接 409 让用户刷新拿最新状态，语义清晰且不堆积请求 |
| A1 索引 | 部分唯一索引怎么兼容两种数据库？ | SQLAlchemy `Index` 的 `sqlite_where` / `postgresql_where` 方言参数按方言择一生效 |
| B1 窗口函数 | 为什么不用子查询取末条？ | 窗口函数一次扫描即可按分区取 rn=1，子查询需相关子查询逐会话执行，无法批量 |
| B2 ZSet | 为什么不用时间戳？ | 同刻度多消息无法区分，`>` 丢消息、`>=` 重复推；单调序号的 `(N,+inf]` 精确不重不漏 |
| B2 ZSet | INCR 和 ZADD 之间要不要事务？ | 不需要——补发取区间而非连续序列，序号空洞不破坏语义（源码注释有明确论证） |
| C1/C2 AI | 模型挂了怎么办？ | 30s 超时 + 异常统一转中文业务文案 + `app_config` 开关可一键关闭；前端按 `/api/ai/status` 隐藏入口 |
| C1/C2 AI | 有没有流式输出 / 结果缓存 / Token 计量？ | **如实回答：没有**。这是可改进项，可主动说"下一步会补 Redis 结果缓存与 SSE 流式" |
| D1 404 | 为什么是 404 不是 403？ | 403 确认资源存在等于给扫描者发地图，404 隐藏管理端存在性 |
| D2 滑块 | 为什么不用极验？ | 自部署需离线可用、无外网依赖；且 SVG 明文会泄露缺口坐标，故返回 PNG 位图 |
| D2 滑块 | 图像生成为什么不阻塞？ | Pillow 绘制与 PNG 编码是同步 CPU 密集，`asyncio.to_thread` 委派线程池，避免注册高峰独占事件循环造成 P99 抖动 |
| E1 trace | 为什么用注释而不是加一列？ | 注释对数据库透明（不改语义与执行计划），却是唯一能原样出现在慢查询日志的载体 |
| E2 热更新 | 为什么原地 setattr 而非重建单例？ | 数十个模块在导入期就绑定了 `settings` 引用，重建会让它们静默指向旧对象 |
| 降级 | 没 Redis 系统还能用吗？ | 能：Redis→内存 dict（限流/验证码/缓存语义对齐）、MinIO→本地盘、Meili→SQL LIKE、WS 广播→进程内直发，功能退化但服务不中断 |

**主动承认的改进项**（被问"有什么不足"时用，显得诚实且有判断力）：
1. Refresh Token 未做轮换与复用检测，旧 refresh 在 7 天内仍有效 → 改进：刷新时轮换并检测 jti 复用，命中即吊销整条令牌族。
2. 限流是固定窗口而非令牌桶，窗口切换瞬间可承受 2 倍阈值 → 改进：改滑窗或 Lua 令牌桶。
3. Meilisearch 检索通道已设计但索引同步任务未接线，当前实际走 SQL LIKE 降级 → 改进：在物品创建/删除后补 `.delay()` 触发。
4. `/metrics` 端点已暴露但计数器未在中间件埋点，指标恒为 0 → 改进：在网关中间件尾部补 `.inc()/.observe()`。
5. 前端单测仅 14 例，覆盖偏轻 → 改进：补充请求层与 WebSocket 客户端的边界用例。
