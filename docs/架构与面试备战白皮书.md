## 第一部分：项目背景与业务复杂度剖析（体现"产品思维"）

### 1.1 业务痛点：不是"做个校园平台"那么简单

CampusSphere 是面向高校学生的校园生活平台，核心域覆盖**二手交易、课程评价、组队活动**三大高频场景。它的技术痛点不是"功能多"，而是**高并发下的几类经典反模式在单进程内同时爆炸**：

1. **多角色权限混乱（学生 / 管理员 / 审计）**
   重构前，权限判断以两种形式散落在业务代码：
   - 路由层 `require_owner(item.owner_id, user)` 只表达"是不是本人"，无法表达"管理员可越权"；
   - Service 层一旦需要"管理员可操作他人资源"，就只能在业务里写 `if user.is_admin`，把鉴权耦合进业务逻辑。
   后果：新增"审计员只能看审计日志、不能改业务数据"这类合规需求时，必须改一堆 Service 代码，且极易漏改导致越权。

2. **高并发下图片验证码拖死接口**
   滑块验证码的 Pillow 出图是**纯 CPU 密集计算**。重构前它在异步协程里直接 `image.save`，等于在 FastAPI 事件循环里做重活，**整个事件循环被阻塞**，其它所有请求被迫排队，接口 RT 从毫秒级劣化到秒级。

3. **配置变更需重启导致运维窗口长**
   教务侧配置（如二手物品发布规则 `items.rules`、功能开关）原本改完要等运维半夜重启服务。重构前没有运行时配置通道，任何 YAML 调整都要走发布流程。

4. **WebSocket 断线丢消息导致交易纠纷**
   二手交易的议价、组队邀请走 WebSocket 实时推送。原实现按"时间戳 `since`"做断线补发：毫秒级并发下多条消息撞同一时间戳，要么**丢消息**（同刻度消息被 `>` 排除），要么**重推**（放宽成 `>=` 又重复）。学生端"我明明发了报价他没收到"的纠纷直接源于此。

**一个真实的越权案例（说明痛点不是纸面）**：某次需求要"管理员能下架任何人的违规物品"，旧代码在 `item.service` 里写 `if current_user.is_admin: allow`。但当"封禁用户"功能上线，`User.status==1` 的判定只在路由层 `require_owner` 里，Service 层的 `is_admin` 分支**完全绕过封禁检查**——被封禁的管理员仍能下架物品。根因就是权限与状态判断散落两处、无统一主体模型。重构后，封禁/禁用判定收口在 `get_principal` 一处（`user.status==1 → 403`、`admin.disabled → 403`），`require_scope` 只管"能做什么"，不再与状态耦合。

**一个真实的交易纠纷案例**：学生 A 给学生 B 发二手书报价，同一毫秒 B 也发来还价。旧 `since=时间戳` 补发用 `>` 游标，A 的报价与 B 的还价落在同一毫秒刻度，A 重连后只收到 B 的还价、自己的报价被 `>` 排除——A 以为"报价没发出去"再次发，造成重复报价、价格错乱，催生客诉。这正是 Task 5 要根治的。

### 1.2 领域模型映射：用户-资源-行为三元组 + 审计影子权限

把三个业务域抽象为统一原语，是后续一切治理层（权限、规则、染色）能复用的前提：

- **用户（Principal）**：发起动作的主体，身份分两套——平台 `User`（JWT `sub`=user.id）与后台 `AdminUser`（JWT `sub`=admin.id）。
- **资源（Resource）**：二手物品、课程评价、组队帖，统一为带 `owner_id` 的实体。
- **行为（Action）**：发布、评价、议价、拉黑……统一为"某用户对某资源施加某作用域的操作"。

**审计影子权限（audit scope）**是合规落点：校方要求审计员能查看操作留痕，但**绝不能**因此获得"改业务数据"的能力。所以它被设计成**独立的只读分支**——`audit ⊃ read`，但 `audit` 不蕴含 `write`。一条 `audit:view` 权限码只映射出 `AUDIT` 作用域，绝不外溢到写/管。这就是"职责分离"在作用域偏序里的具象化。

> **面试话术（产品思维）**：「我们把校园场景抽象成用户-资源-行为三元组，所有业务域共用一套治理原语；审计不是'超级只读管理员'，而是独立分支——它只蕴含 read，不蕴含 write，从作用域偏序上就杜绝了审计员改数据的可能。这是把校方合规要求做进了权限模型，而不是靠人工约定。」

## 第二部分：架构全景与 FastAPI 特性选型理由（体现"技术判断力"）

### 2.1 为什么是模块化单体（Modular Monolith）而非微服务？

**结论**：校园项目并发量适中（峰值远未到需要独立扩缩容的程度），模块间存在**强一致事务**（典型如"发布物品自动触发索引同步"），单体可保证 ACID；但代码按业务域**严格分包**（`app/modules/item`、`app/modules/message`、`app/modules/audit`…），模块间只通过依赖注入与领域事件通信，**为未来拆微服务预留了清晰切口**。

- **选单体不踩坑**：跨模块事务（发布物品 → 同步搜索索引 → 写操作日志）在单体里是一个 DB 事务，强一致；上了微服务就要引入 Saga/最终一致，对校园项目是过度设计。
- **运维简单**：一个进程、一个部署单元、一个 DB，排障链路短。
- **预留切口**：每个 module 自持 router / service / schemas / models，依赖只朝下（core 层），无横向循环依赖。哪天 `message` 模块真成了瓶颈，可以整体抽成独立服务而不必重写。
- **降级不中断的全局约定**：Redis / MinIO / Meili 缺失时一律内存降级，连接不断、功能退化，这必须在单体层统一封装（见各 Task 的降级策略）。

**分层与依赖方向（文字版架构图）**：
```
                ┌──────────────── 接入层 ────────────────┐
   Nginx →  ASGI App (FastAPI)
                │  middleware( trace_id / 网关404 / 异常处理 )
                ├──────────────── 应用层（按域分包）────────────────┐
                │  app/modules/{item,message,audit,admin,auth}…   │
                │    router(声明式Scope) → service(纯业务) → schemas │
                ├──────────────── 核心层 core ────────────────┐
                │  deps(Scope) / database(染色) / config_reload  │
                │  / redis(cache+降级) / logging(trace_id)       │
                ├──────────────── 基础设施层 ────────────────┐
                │  PostgreSQL(asyncpg) / Redis / MinIO / Meili │
                └────────────────────────────────────────────┘
```
依赖只允许"上层 → 下层 / 同层 module 互不横向依赖"。`core` 不反向依赖任何 `module`，这是未来把某个 `module` 整体抽成微服务时的"切割线"。

**为什么不用 Celery / ARQ 做 CPU 隔离？** 验证码渲染是**请求内同步出图**（用户等这张图才能滑），它不是"后台异步任务"——用 Celery 会引入 broker + worker 进程 + 序列化往返，反而增加延迟与运维面。正确做法是在**当前请求协程内**用 `asyncio.to_thread` 把 CPU 段临时让出事件循环，图出来立刻返回。Celery 适合"发邮件、生成报表"这类可延迟的 Job，二者适用域不同，不能混为一谈。

### 2.2 为什么选 FastAPI 而不是 Django / Flask？

| 维度 | FastAPI | Django | Flask |
|------|---------|--------|-------|
| 原生异步 | ✅ `async def` 一等公民，原生支持 WebSocket 长连接 | ⚠️ 异步支持晚、生态割裂 | ⚠️ 需自己拼 async（如 quart），非原生 |
| 校验性能 | ✅ Pydantic V2（Rust 内核），业务规则左移到类型系统 | ⚠️ Form/ModelForm 偏重量、非类型驱动 | ❌ 无内置校验，靠 marshmallow 等第三方 |
| 依赖注入 | ✅ 声明式 `Depends`，可参数化、可请求级缓存 | ⚠️ 中间件/信号，非路由级声明 | ❌ 基本没有 |
| 契约测试 | ✅ 自动生成 OpenAPI，前后端契约可机器校验 | ✅ 有，但偏重 DRF | ❌ 自行维护 |
| 性能 | ✅ 接近 Node/Go 的异步吞吐 | ⚠️ 同步为主 | ⚠️ 同步 |

**关键判断**：
1. **原生异步应对 WS 长连接**——WebSocket 是本项目刚需（议价/组队实时性），FastAPI 的 `websocket_endpoint` 与 `Depends` 同生态，长连接不阻塞事件循环。
2. **Pydantic V2 把业务规则左移**——金额校验、跨字段联动在请求入口就卡死，不污染 Service（详见 Task 2）。
3. **DI 系统强大**——`Depends` 的参数化依赖工厂 + 请求级缓存，直接撑起声明式权限（Task 1）。
4. **OpenAPI 契约**——前后端联调有机器可校验的契约，减少"字段对不上"的扯皮。

> **面试话术（选型）**：「选 FastAPI 不是赶时髦。二手交易/组队对实时性要求高，WebSocket 长连接必须不阻塞事件循环，这是 Flask 的短板；业务规则我要求左移到类型系统、用 Pydantic V2 在入口卡死，而不是散在 Service 里；权限治理靠 `Depends` 的声明式依赖。这三件事 Django/Flask 都要自己造轮子，而 FastAPI 原生给。微服务我明确没上——校园并发量不需要独立扩缩容，跨模块强一致事务在单体里一个事务搞定，拆了反而引入分布式事务的复杂度。」

## 第三部分：六大核心亮点深度解析

> 每个亮点按 **[技术难点] → [FastAPI 底层原理运用] → [业务价值] → [面试话术]** 展开，并附**实测验证数据**。

### 亮点 1（Task 1）：声明式权限作用域（替换全 Service 层 if-else）

**[技术难点]**
平台存在**两套并存身份体系**——平台 `User`（用 `is_admin` 布尔位提权）与后台 `AdminUser`（用 `role_id`→`Role.permissions` 做 RBAC）。`/api/admin/login` 签发的 AdminUser 令牌，其 `sub` 在 `users` 表查不到；平台用户也不是 AdminUser。解析主体必须**两边都查**，只查一边就废掉另一套身份。
第二难：异步 ORM 下，`AdminUser.role` 是普通 lazy 关系，直接访问会抛 **`MissingGreenlet`**（隐式 IO 不被允许）。必须显式预载。
第三难：如何把"读/写/管/审计"四权及"本人或管理员可越权"表达清楚，又不回到 Service 层 if-else。

**[FastAPI 底层原理运用]**
- **参数化依赖工厂**：`require_scope(scope)` 是个工厂函数，返回闭包 `_dependency`。`require_scope("admin")` 因此能参数化出任意多个彼此独立的依赖实例（`_dependency.__name__ = "require_scope_admin"`，便于 OpenAPI/测试识别）。
- **请求级依赖缓存**：FastAPI 默认 `use_cache=True`，同一请求内 `get_principal` 只执行一次，所以路由上叠加多个 `require_scope` 不会重复查库（源码注释明写：`require_scope` 把"需要什么权限"声明在**路由层**，Service 层零权限耦合）。
- **作用域偏序 + `selectinload`**：`_SCOPE_IMPLIES` 定义 `admin⊃write⊃read`、`audit⊃read`；`get_principal` 用 `select(AdminUser).options(selectinload(AdminUser.role))` 显式预载 role，根治 `MissingGreenlet`。
- **资源级归属**：`require_owner_or_scope(owner_id, principal, Scope.ADMIN)` 表达"本人 或 持 admin 作用域者"放行，作用域只管"是什么角色"，归属管"是不是他的记录"。

**[业务价值]**
新来的审计员只需在 `Role.permissions` 里挂 `audit:view`，路由层 `Depends(require_scope("audit"))` 自动生效，**业务代码零改动**。最小权限原则：未登记的权限码只得到基础 read/write，新增权限码不显式登记不额外授权。
**验证**：`tests/unit/test_scope_deps_unit.py` **12 passed**；`test_audit_logs` 经 `register_exception_handlers` 后 `BizError` 被统一包装为 `code/msg`。

**[面试话术]**
「我们没有把 `if user.is_admin` 撒在 Service 层。我用一个参数化依赖工厂 `require_scope(scope)` 把'需要什么权限'声明在路由上，FastAPI 的请求级缓存保证同请求只查一次库。难点有两个：一是平台用户和后台管理员两套身份要同时解析，二是异步 ORM 下 AdminUser.role 的 lazy 加载会抛 MissingGreenlet，所以我用 `selectinload` 显式预载。审计是独立只读分支，从作用域偏序上就隔离了'改数据'的能力。」

### 亮点 2（Task 2）：Pydantic V2 业务规则引擎（领域模型驱动力）

**[技术难点]**
前端发来的 JSON 经 Pydantic lax 模式会做**隐式类型转换**——典型地 `{"price": true}` 会被静默转成 `1`，`{"price": "3.9"}` 转成 `3.9`。如果后端不守门，布尔/浮点/字符串就混进了金额字段。另一难是**跨字段联动**：电子类目强制图片数、`on_sale` 且 `price==0` 应禁止。

> ⚠️ **前提校正（重要）**：需求里说的"后端做元→分"和"电子产品强制三图"两处原始前提**均不成立**：
> - 元→分：**前端已 `toCents()` 转换**，后端不再 ×100（已与用户确认），故 `price` 保持整数分，后端只做**防御性兜底**校验。
> - 三图：`config/school.yaml` 的 `items.rules.electronics_min_images` **默认 `0`（关闭）**，因为前端 `MarketPublish.tsx` 已要求 ≥1 图，硬开 3 会破坏真实用户与测试。引擎**支持按配置强制 N 图**，但并非硬编码为 3。

**[FastAPI 底层原理运用]**
- **`field_validator(mode="before")`**：在校验前拿到**原始输入**做类型守卫，`_validate_cents` 显式拒绝 bool/float/str 的 lax 隐式转换，上限 `MAX_PRICE_CENTS=99_999_900`（约 100 万元）。
- **`model_validator(mode="after")`**：`ItemCreate/_check_cross_field_rules` 做跨字段业务规则——按 `electronics_min_images` 配置强制图片数、`price==0` 且 `ON_SALE` 禁止。
- **契约归一**：校验错误由 `BizError` 统一抛出，经异常处理器归一成 `{"code":0,...}` 风格的错误体。

**[业务价值]**
金额/类目规则**左移到类型系统**，Service 层不再写字段级 if。后端只做防御，不重复前端逻辑——这是**成熟的前后端契约对齐**：前端负责转换与体验，后端负责不被绕过。配置化（N 图阈值）让规则可运营，不需改代码。
**验证**：`tests/unit/test_item_schema_rules_unit.py` **15 passed**。

**[面试话术]**
「业务规则我左移进了 Pydantic V2。金额用 `field_validator(mode="before")` 在类型转换前就拦住 bool/float 的隐式转换——你发 `{"price": true}` 我直接拒绝，而不是让它变成 1。跨字段联动用 `model_validator(mode="after")`。关于元转分：这是个被证伪的前提，前端已经 toCents 了，后端再做是重复且易错，所以后端只做防御性兜底。这体现了前后端契约对齐——转换归前端，不被绕过归后端。」

### 亮点 3（Task 3）：CPU 密集型任务隔离（防止阻塞事件循环）

**[技术难点]**
滑块验证码的 Pillow 出图是**纯 CPU 计算**（图像缩放、合成、编码）。若直接在 `async def` 端点里 `image.save()`，它占据事件循环线程，期间**所有其他协程无法被调度**——一个验证码接口就能拖垮整个服务的并发。

**[FastAPI 底层原理运用]**
- 抽出**纯同步、无 IO** 函数 `_render_slider_images(target_x, target_y) -> tuple[str,str]`（返回 data URI）。
- `generate_slider()` 改为 `await asyncio.to_thread(_render_slider_images, target_x, target_y)`，把同步重活 offload 到**默认线程池**，事件循环立即交还其它协程。
- 底层用 FastAPI/Starlette 自带的 `asyncio.to_thread`（即 `run_in_executor` 的语法糖），复用进程级线程池，无需自建。

**[技术实证（可证伪的控制实验）]**
`tests/unit/test_captcha_thread_offload_unit.py` 用 **monkeypatch 把 `asyncio.to_thread` 替换成"直接在事件循环里同步调用"**（即重构前的写法），断言**立刻失败**——这证明测试不是在"表演通过"，而是真测出了"去掉 to_thread 事件循环就被阻塞"。测试通过"在渲染前后向事件循环投递哨兵任务、验证其是否被及时调度"来衡量**事件循环响应性**，而非发布 RPS 数字（RPS 受机器影响，不具备可移植可信度）。
**验证**：**4 passed**（含控制实验）。

> 诚实说明：交付物未公布"加 to_thread 前后具体 RPS 差值"，因为该指标依赖机器且易误导。我们测的是**确定性更强**的"事件循环是否被阻塞"——这是 this bug 的根因，控制实验足以证伪"不隔离也行"的假设。

**[业务价值]**
验证码接口不再拖累全局 RT，高峰期并发稳定。
**面试话术**：「Pillow 出图是 CPU 活，我把它抽成纯同步函数，用 `asyncio.to_thread` 丢进默认线程池，事件循环立刻腾出来服务别的请求。我特意写了个可证伪的单测：把 to_thread 替换回同步调用，测试立刻挂——证明不是写了个好看的 offload，是真的解决了阻塞。」

### 亮点 4（Task 4）：基于 Redis Pub/Sub + ASGI Lifespan 的配置热更新（零停机运维）

**[技术难点]**
配置（如 `school.yaml` 的 `items.rules`、功能开关）改完要生效，传统做法是重启。难点：① 如何在不重启的前提下刷新一个**模块导入期就绑定的 `settings` 单例**；② 如何用 ASGI 生命周期承载一个**长驻后台订阅协程**；③ Redis 宕机时不能让服务崩，要优雅降级 + 慢重试。

> ⚠️ **前提校正（重要）**：需求里"教务老师改邮箱白名单"的例子**前提不成立**——邮件白名单本就是实时读 DB，`email_register 属性热更` 是伪需求。实际热更对象是 `school.yaml` **静态配置**（二手物品规则、功能开关等）。

**[FastAPI 底层原理运用]**
- **ASGI Lifespan 承载后台常驻协程**：`app/main.py` 的 `lifespan` 上下文里 `await start_config_reloader()`，finally 里 `await stop_config_reloader()`——订阅监听协程与应用同生共死，绕过了"请求结束即回收"的常规依赖生命周期。
- **`asyncio.to_thread` 刷新单例**：`reload_settings` 用 `asyncio.to_thread(settings.load_school_config)` 同步读 YAML 并**就地刷新**全局 `settings` 单例，模块导入期绑定的 `settings` 引用无需重启即生效。
- **Redis Pub/Sub 热通道**：`publish_config_reload(reason)` 发到 `CONFIG_RELOAD_CHANNEL="config:reload"`，失败返回 0 不抛；`_listen()` 长驻订阅循环在 Redis 不可用时**优雅降级 + 30s 慢重试 + 坏消息自愈**。
- **兜底端点**：`POST /api/admin/config/reload` 先 `publish_config_reload` 再本地 `reload_settings` 兜底，receivers==0 时标记降级。

**[业务价值]**
教务老师改 `school.yaml`（如调二手物品规则、开功能开关）**无需等运维半夜重启**，运维窗口趋近于零。
**验证**：`tests/unit/test_config_hot_reload_unit.py` **6 passed**（含全局单例污染还原）。

**[面试话术]**
「配置热更新我用 ASGI Lifespan 起一个长驻订阅协程，监听 Redis 的 config:reload 频道；收到消息后用 to_thread 把 YAML 重新读进 settings 单例，模块导入期绑定的引用就地生效，不用重启。关键是降级：Redis 挂了我不崩，而是 30 秒慢重试、坏消息自愈。另外有个前提我纠正过——邮件白名单本来就是实时读 DB，真正热更的是 school.yaml 静态配置，别被伪需求带偏。」

### 亮点 5（Task 5）：WebSocket 应用层 Ack + Redis ZSet 精准补发（解决消息可靠性）

**[技术难点]**
原补发按时间戳 `since`：毫秒级并发下多条消息撞同一刻度，要么丢（同刻度被 `>` 排除）要么重（`>=` 又重复）。**时间戳作为游标在并发下语义不精确**。

**[FastAPI 底层原理运用]**
- **客户端维护本地 Seq + 服务端 Redis ZSet**：`LocalSeqStore` 用 Redis `INCR` 作 score 分配单调序号，`ZADD` 写入 ZSet（member=消息体，score=seq）。
- **开区间取缺量**：`since(conversation_id, last_seq)` 用 `ZRANGEBYSCORE (last_seq +inf`——**开区间**不含客户端已确认的那条，补发区间 `(N, +∞]`，**不重不漏**。
- **应用层 Ack**：客户端重连时上报 `last_seq`，服务端按游标精确补发；在线推送与离线补发共用同一 seq。
- **降级**：Redis 不可用时退化为进程内序号表（单实例语义正确，多实例各发各的号，符合"降级不中断"总约定）。上限 500 条，长离线走历史消息接口。
- **修复真实缺陷**：旧 `_compensate`（时间戳口径）**从未被调用**，本次补发逻辑替换它并补了守护测试。

**[残酷教训（加分项）]**
Starlette TestClient 下，**发送方必须 `receive_json()` 排空自己的回声**，否则 `publish`→`send_json` 在单线程 portal 里积压，级联占满数据库连接池 → DB 死锁。这证明**测试环境的单线程并发模型与生产不一致**，WS 测试必须显式排空回声。
**验证**：`tests/unit/test_ws_seq_unit.py` **12 passed**；`tests/test_websocket.py` 新增 **3 个集成测试全过**（含"修前 `_compensate` 死代码"守护），该文件共 **7 passed**。

**[面试话术]**
「时间戳做断线补发游标是不行的——毫秒级并发会撞时间戳，要么丢要么重。我让客户端维护本地序号 last_seq，服务端用 Redis ZSet，score 就是 seq，补发用开区间 `(last_seq` 一次取回，不重不漏。在线和离线补发共用同一套 seq。测试时踩了个深坑：TestClient 是单线程，发送方不排空自己的回声，send_json 积压会级联成 DB 连接池死锁——这暴露了测试并发模型和生产不一致，所以我的 WS 测试都显式 receive_json 排空。」

### 亮点 6（Task 6）：全链路可观测染色（X-Request-ID 穿透 SQL 注释）

**[技术难点]**
慢 SQL 日志孤立于业务日志，排查时只能靠时间戳去猜"哪条 SQL 属于哪个请求"。要把 **Nginx 访问日志 → 业务日志 → 慢 SQL** 三条线串起来，必须把请求 ID 穿透到 DB 侧——而 DB 侧唯一能透明承载的载体是 **SQL 注释**（不改写语义、不影响执行计划，却原样出现在慢查询日志 / `pg_stat_statements` / 云厂商 SQL 洞察）。

**[FastAPI 底层原理运用]**
- **`contextvars` 异步上下文穿透**：`logging.py` 定义 `_trace_id_var = ContextVar("campus_trace_id")`，中间件生成 `X-Request-ID` 并 `bind_request`，跨 `Depends`/异常处理器/DB 驱动贯穿同请求上下文（即便中间 await 切协程也不丢）。
- **`sanitize_trace_id` 防注入**：X-Request-ID 来自客户端请求头，必须正则 `[^A-Za-z0-9_.:-]` 过滤并截断 64 字符——否则 `*/ DROP TABLE users; --` 能**闭合注释块注入**。单测专门喂 `x */ DROP TABLE users; --` 断言被净化。
- **方言级 `do_execute` 接管**：见第四部分。最终 `database.py` 用 `@event.listens_for(engine.sync_engine, "do_execute")` 自己 `cursor.execute(commented, parameters)` 并返回 `True` 告知 SQLAlchemy "已接管"。

**[业务价值]**
每条慢 SQL 自带 `/* trace_id=xxx */`，从 Nginx 到业务到 DB 一线串联，慢 SQL 溯源从"靠猜"变成"一键追"。
**验证**：`tests/unit/test_trace_id_unit.py` **14 passed**（Mock cursor 断言注入 + 接管；`do_execute` 接管把真实执行的 `SELECT 42` 改写成 `SELECT 99` 的 oracle 端到端验证）。

**[面试话术]**
「全链路染色我用 contextvars 把 X-Request-ID 穿透到 DB 驱动，再用 SQL 注释载体注入每条语句——注释对数据库透明，却原样出现在慢查询日志里。关键点：X-Request-ID 是客户端给的，我必须 sanitize 防注释闭合注入，否则 `*/ DROP TABLE` 能打穿。SQLAlchemy 2.0.30 的 before_cursor_execute 返回值被忽略，我翻源码发现后改用 do_execute 接管才真正生效。」

### 第三部分补：六个亮点的"面试官反例"与设计取舍（背这个才不会被问倒）

每个亮点都有人能挑刺。提前准备反例，比只会讲优点更显老练。

- **亮点 1 反例**：「参数化依赖每次请求都 new 一个闭包，会不会有性能/内存问题？」→ 不会。闭包是轻量对象，且 `get_principal` 经请求级缓存只跑一次；作用域展开 `_expand` 用 `lru_cache(maxsize=8)` 缓存编译期常量。真正开销是那一次 `selectinload` 查库，已无法再省。
- **亮点 2 反例**：「mode=before 拦了 bool，那 `{"price": 1.0}` 浮点呢？」→ 同样拦。`_validate_cents` 拒绝一切非 int 原始类型；即便 lax 把它转成 1，我们也不依赖转换，而是先判类型再判值。上限 99999900 分防止极端大数撑爆金额字段。
- **亮点 3 反例**：「to_thread 把活丢进默认线程池，线程池打满怎么办？」→ 默认池有限，但验证码是低频且短任务；且我们只在"纯 CPU 同步段"用 to_thread，不塞 IO 进去，避免占满执行器饿死其他调用方（源码注释明写此约束）。
- **亮点 4 反例**：「Redis 宕机期间改的配置，恢复后会不会丢？」→ 不丢语义正确性，但恢复瞬间订阅协程重连后会继续收新消息；历史丢失的那次 reload 因有 `/api/admin/config/reload` 本地兜底 + receivers==0 标记降级，运维可手动补一发。这是"最终一致"取舍，不是 bug。
- **亮点 5 反例**：「ZSet score 用 INCR，Redis 重启序号不连续了怎么办？」→ 游标语义是区间 `(N, +∞]`，**不要求连续**，空洞不影响补发；且 500 条滚动窗口内本就允许空洞。
- **亮点 6 反例**：「contextvars 在多线程 to_thread 里会丢吗？」→ 会丢——to_thread 切换到线程池时上下文不自动跟随。但染色只在 DB 驱动（同协程链路）读取，to_thread 内部的同步函数不查库，故无影响；若未来要在 to_thread 内查库，需显式 `contextvars.copy_context().run(...)` 传递，这是已知边界。

## 第四部分：最难解决的 Bug 实录（体现"硬核调参/调试能力"）

### 4.1 SQLAlchemy 2.0 Hook 失效：从 before_cursor_execute 到 do_execute

**现象**：想在每条 SQL 前注入 `/* trace_id=xxx */`，按直觉用 `before_cursor_execute` 监听器返回改写后的语句。上线观测却发现**数据库执行的仍是原语句**，注释没出现。

**排查（源码级）**：监听器**确实被调用**、**确实返回了改写语句**，但 SQLAlchemy 2.0.30 在 `before_cursor_execute` 路径上**忽略了返回值**（`Core select` 与 `text()` 两条路径、Engine/Connection 实例级与类级四种注册方式均如此）。`database.py` 源码注释明确记录："监听器被调用、也返回改写后的语句，但数据库执行原语句（SELECT 42→99 oracle 验证）"。

**解决**：放弃"返回值改写"，改为**方言级接管**——`@event.listens_for(engine.sync_engine, "do_execute")` / `"do_execute_no_params"` 里自己 `cursor.execute(commented, parameters)` 并 `return True`，告知 SQLAlchemy "已处理，无需再执行"。无 trace 上下文（后台任务/lifespan）时返回 `False` 交回默认路径。

**复现与验证步骤（可独立复现）**：
1. 在测试里向真实引擎注册一个 `before_cursor_execute` 监听器，返回把 `SELECT 42` 改成 `SELECT 99` 的语句；
2. 执行 `SELECT 42`，断言返回仍是 `42` → 证明返回值被忽略；
3. 改用 `do_execute` 接管，内部 `cursor.execute("SELECT 99")` 并 `return True`，再执行断言返回 `99` → 证明接管生效。
这两步就是 `test_trace_id_unit.py::test_do_execute_takeover_changes_executed_sql` 的端到端 oracle。

**实证**：`test_trace_id_unit.py` 用 `SELECT 42 → SELECT 99` 的 oracle 用例证明 `do_execute` 接管**确实改变了数据库实际执行的语句**，而非仅改了日志字符串。**14 passed**。

### 4.2 TestClient WebSocket 死锁：单线程回声积压级联 DB 死锁

**现象**：WS 集成测试偶发卡死，最终报数据库连接池耗尽。

**根因**：Starlette TestClient 跑在**单线程 portal** 下。测试里发送方 `publish` 一条消息后，自己的回声也被 `send_json` 推回队列；若测试**不 `receive_json()` 排空回声**，消息在单线程里积压 → `publish` 协程长期占用 → 其持有的 DB 连接无法释放 → 连接池被占满 → 其它需要 DB 的请求/协程死锁。这是**测试环境并发模型 ≠ 生产**导致的假死，与业务代码无关。

**解决**：所有 WS 测试显式 `client.receive_json()` 排空发送方自身回声；并在 `tests/test_websocket.py` 加 3 个集成测试守护（含"旧 `_compensate` 死代码"守护）。**7 passed**。

> 这两个坑已沉淀为项目 skill `sqlalchemy-testclient-gotchas`，可复用。

## 第六部分：面试必问 Q&A 模拟（15 个）

**Q1. 你们的 WebSocket 怎么保证消息不丢？**
→ 引导到 Task 5：时间戳 `since` 会撞毫秒刻度导致丢/重。我们让客户端维护本地 `last_seq`，服务端用 Redis ZSet（score=seq），补发用开区间 `(last_seq` 一次取回，不重不漏。在线/离线共用同一 seq。

**Q2. Redis 挂了，你们的配置热更新和 WebSocket 会怎样？**
→ 双降级：配置订阅循环 30s 慢重试 + 坏消息自愈，不崩；WS 序号退化为进程内表（单实例语义正确，多实例各发各的号，但连接不断、功能退化）。整体遵循"降级不中断"。

**Q3. 为什么用 `asyncio.to_thread` 而不是自己建 ThreadPool？**
→ 复用 FastAPI/Starlette 进程级默认线程池，省去自己管理池大小/生命周期；`to_thread` 是 `run_in_executor` 的语法糖，语义清晰。自建池反而易与框架池打架、难统一容量治理。

**Q4. 你们后台管理网关只返回 404 防扫描，具体怎么实现的？**
→ 真有此机制（已验证）：`app/modules/admin/gateway.py` 中，`/api/admin/*`（discover 除外）未携带有效 `X-Admin-Gateway` 令牌时，中间件 `middleware.py` 故意返回 **404 而非 401/403**，对外表现得像端点不存在；`discover` 用网关密钥换短时 HMAC 令牌，密钥错误同样 404。这是"安全通过 obscurity + 真实鉴权"的双层。

**Q5. `before_cursor_execute` 失效你怎么发现的？Github Issue 搜的吗？**
→ 不是搜到的。我写了 SELECT 42→99 的 oracle 测试，发现监听器被调用、返回改写语句，但 DB 执行原语句——说明返回值被忽略。再读 SQLAlchemy 2.0.30 源码确认 `before_cursor_execute` 该路径不消费返回值，遂改用 `do_execute` 接管（自己 `cursor.execute` 并 return True）。读源码 > 搜 Issue。

**Q6. 你这个权限模型，新增一个"版主"角色要改多少代码？**
→ 零改业务代码。在 `Role.permissions` 加权限码，在 `_PERMISSION_SCOPE_MAP` 登记其映射到的 Scope（如 `mod:delete→WRITE`），路由层 `require_scope` 自动生效。最小权限：未登记码只给基础 read/write。

**Q7. 为什么 audit 不蕴含 write？**
→ 合规要求：审计员看操作留痕，但绝不能改业务数据。所以 `audit⊃read` 且独立成支，从作用域偏序上就隔离了写能力，不是靠人员自觉。

**Q8. Pydantic 的 `mode="before"` 和 `mode="after"` 你分别用来干嘛？**
→ before 拿原始输入做类型守卫（拦 bool/float 隐式转换进金额）；after 做跨字段业务规则（类目图片数、on_sale 且 price==0 禁止），此时各字段已校验完，可安全联动。

**Q9. 元转分为什么后端不做？**
→ 前提被证伪：前端已 `toCents()`，后端再做是重复且易错。后端只做防御性兜底（拒绝非法类型、设上限 99999900 分）。这是前后端契约对齐——转换归前端，不被绕过归后端。

**Q10. 配置热更新怎么保证多 worker / 多实例都刷到？**
→ Redis Pub/Sub 是广播，所有实例的 Lifespan 订阅协程都收到 `config:reload` 并各自 `to_thread` 刷新本地 `settings` 单例；`/api/admin/config/reload` 再补本地刷新兜底，receivers==0 标记降级。

**Q11. 你的 trace_id 注入会不会有 SQL 注入风险？**
→ 会防范。`sanitize_trace_id` 用正则 `[^A-Za-z0-9_.:-]` 过滤并截断 64 字符，单测专门喂 `*/ DROP TABLE users; --` 断言被净化，杜绝注释块闭合注入。

**Q12. 你们为什么不上微服务？**
→ 校园并发量不需要独立扩缩容；跨模块强一致事务（发布物品→索引同步→操作日志）在单体一个事务搞定，微服务要引入 Saga/最终一致，过度设计。但按业务域严格分包，预留了拆服务的切口。

**Q13. 断线补发的 ZSet 会无限增长吗？**
→ 不会。`ZREMRANGEBYRANK` 裁剪，只保留最近 500 条（DEFAULT_MAX_ENTRIES=500）；长时间离线应走历史消息接口而非让 ZSet 膨胀。

**Q14. 你这套染色对性能影响多大？**
→ 极小。contextvars 读写是协程局部变量，零锁；`do_execute` 仅做一次字符串拼接 + `cursor.execute`，不改执行计划。注释对 DB 透明。

**Q15. 你测了 371 个用例，零回归是怎么保证的？**
→ 每个 Task 配独立单测（Scope 12 / Schema 15 / Captcha 4 / Config 6 / WS 12 / Trace 14），外加 WS 集成 3 例与全量基线 305→371（净 +66）。CI 以 `FULLSUITE_EXIT=0` 为门禁，新增路径都有守护测试（如旧 `_compensate` 死代码守护），回归即红。

**Q16. 你的 trace_id 在异步链式调用里会串号吗？**
→ 不会。`contextvars` 随协程上下文传递，每次 `await` 切出再切回都保留原值；中间件在请求入口 `bind_request` 写入、响应出口 `clear_request` 清除。唯一边界是 `asyncio.to_thread` 切换到线程池时上下文不自动跟随——但染色只在 DB 驱动（同协程）读取，to_thread 内部的同步函数不查库，故无串号风险。

**Q17. 如果让你现在重做一遍，哪一处会改？**
→ 两处：① WS 补发的 ZSet 容量上限 500 是经验值，若未来出现"长离线 + 高吞吐"叠加，应让客户端在 last_seq 过旧时自动降级走历史接口而非 ZSet 滚动窗口，目前靠约定而非强制；② 配置热更目前只覆盖 `school.yaml`，若后续要热更"邮件白名单"类 DB 配置，应抽象一层"配置源注册表"而非硬编码单文件。其余六处设计经测试与源码验证，保持不变。
