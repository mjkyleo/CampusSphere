## 1. 问题一：食堂页面配置（按武汉大学实际情况、按学期）

### 1.1 现状与根因



* `canteens` 表为空 → 前端 `CanteenList` 拿到空列表。

* 数据模型只有 `食堂(Canteen) → 档口(Stall) → 菜品(Dish)` 三层，`Canteen` 只有 `name/location/image`，**缺少 "学部 / 餐饮区 / 食堂类型 / 楼层 / 描述" 等维度**，无法表达武大食堂的真实结构（4 学部 × 9 餐饮区 × 3 类食堂）。

* 前端 `CanteenOut` 类型已经预留了 `description / opening_hours / rating`，但后端模型没有这些字段 → 前端只能显示默认占位文案。

* 写入只能走管理后台 admin API，没有初始化 / 种子数据。

### 1.3 数据模型方案（已定稿）

在 `Canteen` 上扩展维度字段（`alembic` 迁移，前端 `CanteenOut` 已基本对齐）：



```
class Canteen(Base):

\&#x20;   name: str                 # 食堂名：如 "梅园学生食堂"、"杏园食堂一楼"

\&#x20;   campus: str               # 学部：文理学部 / 工学部 / 信息学部 / 医学部

\&#x20;   zone: str                 # 餐饮区：梅园 / 桂园 / 枫园 / 湖滨 / 工学部 / 田园 / 信息学部 / 星园 / 医学部

\&#x20;   canteen\\\_type: str         # 类型：学生大伙食堂 / 风味食堂 / 教工食堂（梅园CBD 用"风味食堂" + 商业街标签）

\&#x20;   floor: str = ""           # 楼层：如 "一楼 / 二楼 / 三楼"；单层食堂留空

\&#x20;   description: str = ""     # 官方介绍（Text）

\&#x20;   features: list\\\[str] = \\\[]  # 特色标签：如 \\\["小碗菜", "智慧餐盘"]；梅园CBD → \\\["商业街", "品牌餐饮"]

\&#x20;   popular\\\_dishes: list\\\[str] = \\\[]  # 招牌菜：如 \\\["潮楠烧饼", "石锅饭"]

\&#x20;   opening\\\_hours: str = ""   # 营业时间

\&#x20;   semester: str | None = "" # 学期：如 "2026-2027-1"；空 = 长期开放/不随学期变化

\&#x20;   location: str = ""

\&#x20;   image: str = ""
```



* `features` / `popular_dishes` 用 JSON 数组存储（SQLite 存 Text-JSON，PostgreSQL 可换 JSONB）。

* 展示层级：**学部 (学部 Tab) → 餐饮区 (分组) → 食堂 (卡片，含类型 / 楼层 / 描述 / 招牌菜) → 档口 (Stall) → 菜品 (Dish) + 评价 (CanteenReview)**。

* **多楼层食堂（杏园，已定稿・按楼层拆分）**：`杏园食堂一楼 / 杏园食堂二楼 / 杏园食堂三楼` 各为 **1 条 Canteen 记录**（`zone=医学部`，`floor` 分别为 "一楼 / 二楼 / 三楼"），各自独立 `canteen_type`（一楼・学生大伙 / 二楼・风味 / 三楼・风味 + 教工），便于列表独立展示、独立筛选与评价；各楼层招牌菜作为其下 Dish。

* **梅园 CBD（已定稿・标签收录）**：作为 1 条 Canteen 记录进入食堂列表，`canteen_type=风味食堂`，`features` 增加 `商业街 / 品牌餐饮` 标签（瑞幸、茶颜悦色、肯德基等），不单独设入口，与普通食堂一致展示并标注标签。

### 1.5 前端优化（CanteenList / CanteenStall）



* **学部 Tab**：全部 / 文理学部 / 工学部 / 信息学部 / 医学部，切换即过滤（对应 `campus`）。

* **类型筛选**：学生大伙食堂 / 风味食堂 / 教工食堂（对应 `canteen_type`）。

* **餐饮区分组折叠**：学部内按 `zone`（梅园 / 桂园 / 枫园…）分组展示，避免一次性铺开；卡片展示名称、类型角标、楼层、描述摘要、招牌菜标签、评分。

* **多楼层食堂**：杏园 3 条卡片（一楼 / 二楼 / 三楼）独立展示、可分别筛选与点评；梅园 CBD 以 "商业街" 标签与普通食堂同列表展示。

* **学期筛选**：默认当前学期；支持切换（对应 `semester`；无学期标记的食堂始终显示）。

* **详情页（CanteenStall）**：展示完整官方介绍、特色标签、招牌菜、营业时间、档口列表 + 菜品 + 评价。

### 1.6 后端补充字段



* `CanteenCreate / CanteenOut` 补上 `campus / zone / canteen_type / floor / description / features / popular_dishes / opening_hours / semester`，管理后台表单同步支持。

## 4. 问题四：消息是否支持历史消息？

### 4.1 结论：**支持历史消息**，不是 "仅双方在线才能交流"。



* 消息全量落库：`messages`（内容、类型、已读）、`conversations`（会话）、`participants`（每成员已读游标 `last_read_at`）。

* 离线不丢：发送即 `INSERT` 落库；对方不在线也没关系，下次上线 / 打开会话时通过 REST 拉取。

* 前端 `MessageCenter` 流程：进入页面 `GET /api/messages/conversations`（会话列表）→ 选中会话 `GET /api/messages/conversations/{id}`（分页历史）→ 在线时 WebSocket `/ws` 增量推送 + 本地去重 → `POST .../read` 更新已读游标与未读数。

* 会话幂等：同两人 / 同一交易只建一个 `conversation`（唯一约束 `conv_type+related_id`）。

### 4.2 可优化点（建议，不阻塞）



1. **历史分页 / 上拉加载**：目前一次拉一页（默认 50 条）；建议前端 "滚动向上加载更多 + 时间游标"，会话列表支持按更新时间倒序分页。

2. **离线补拉**：WS 重连后，按各会话 `last_read_at` 之后增量拉取，避免漏消息。

3. **会话列表 N+1**：`list_conversations` 对每个会话分别查参与者 / 最后一条 / 未读数，可合并为一次聚合查询，降低 RTT。

4. （可选）消息撤回 / 引用回复：需新增消息状态字段与接口。

## 5. 问题五：二手交易并发是否考虑？有没有用数据库锁？

### 5.1 现状：**存在竞态，未加锁**



* `create_trade_session` 流程是 check-then-act：



```
if item.status != ItemStatus.ON\\\_SALE: raise ...

ts = TradeSession(item\\\_id=..., buyer\\\_id=...)

db.add(ts); await db.commit()
```

两步之间无任何锁 / 原子保护。\*\* 两个买家并发点击 "我想要"\*\* 时，都可能先读到 `ON_SALE`，随后都创建交易会话 → 同一物品出现多个活跃会话；若继续走到成交，还可能对同一物品重复改价 / 改状态。



* `trade_sessions` 表无 `(item_id)` 唯一约束（只有普通索引）；数据库当前 4 个会话分属不同物品，尚未暴露问题，但并发压测下必然出现。

* `mark_as_sold` / 状态更新同样是 "读 - 改 - 写"，无乐观锁（无 `version` 列）。

### 5.2 推荐方案（分层加固，全部建议实施）



1. **原子抢占（核心）**：创建会话前，用**条件 UPDATE** 把物品状态从 `ON_SALE` 原子改为 `RESERVED`：



```
UPDATE items SET status = RESERVED, updated\\\_at = now()

\&#x20;WHERE id = :item\\\_id AND status = ON\\\_SALE;
```



* 受影响行数 = 1 → 抢占成功，允许创建交易会话；

* 受影响行数 = 0 → 已被他人抢先，返回 409 / 明确提示。

* 这样同时保证 "同一物品同一时刻只有一个活跃交易"，且状态机（ON\_SALE→RESERVED→SOLD）自动一致。

1. **DB 唯一约束兜底**：给 `trade_sessions` 加**部分唯一索引**（SQLite/PostgreSQL 均支持）：

* `CREATE UNIQUE INDEX ... ON trade_sessions(item_id) WHERE status = ACTIVE`

* 可选再加 `(item_id, buyer_id) WHERE status = ACTIVE`，防止同一用户对同一物品重复建会话（幂等）。

1. **生产环境（PostgreSQL）补充**：关键事务内用 `SELECT ... FOR UPDATE`（SQLAlchemy `with_for_update()`）锁物品行后再判断；SQLite 下用 `BEGIN IMMEDIATE` 事务。条件 UPDATE 方案在两种库下均成立，可作主实现。

2. **状态变更统一走条件 UPDATE**：`mark_as_sold`、改价、上下架等所有 `items.status` 变更统一改为 "带旧状态条件的 UPDATE"，天然规避 ABA / 重复提交；可选再加 `version` 乐观锁列。

3. **事务边界**：状态抢占 + 会话创建放在同一事务内提交，失败整体回滚。
