# CampusSphere 项目结构与代码分层说明

> 基于当前工作区实际代码整理（2026-09-10）。目标读者：后端维护者 / 代码评审人。

## 1. 整体结论摘要


| 维度           | 结论                                                                                                                                                                |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **项目定位**   | 面向高校的校园综合服务平台（CampusSphere），覆盖二手交易、兼职、资料共享、搭子组队、课程/食堂评价、实时消息等场景。                                                 |
| **后端技术栈** | Python 3.12+、FastAPI（ASGI）、SQLAlchemy 2.0 异步 ORM、Pydantic v2、Alembic、Celery（Redis broker）、Meilisearch、MinIO、Prometheus。                              |
| **架构形态**   | **模块化单体（Modular Monolith）**：单一 FastAPI 应用，按业务域划分 `app/modules/*`，每个域自包含 `router / service / models / schemas`，边界清晰、暂不拆分微服务。 |
| **分层**       | 接口层（router）→ 业务层（service）→ 数据访问层（models + SQLAlchemy），横切基础设施层（`app/core/*`）与异步任务层（`app/tasks/*`）。                             |
| **核心能力**   | 配置驱动多校部署、声明式 Scope 权限、CAS 条件 UPDATE 防超卖、窗口函数/预加载去 N+1、Redis 无感知降级、AI 三层降级、管理员网关隐藏、Prometheus 指标埋点。            |
| **主要风险**   | 全量测试耗时较长（>10 min，需分批）；Meilisearch/AI 等外部依赖默认走降级路径，真实环境需专项验证；部分文档仍存在漂移，应以源码为准。                                |

## 3. 代码分层与职责


| 分层                             | 位置                                                                                      | 职责                                                                                                | 约束 / 约定                                                                                                                                |
| ---------------------------------- | ------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **接口层（Presentation）**       | `modules/*/router.py`、`main.py`、`core/middleware.py`、`core/deps.py`                    | HTTP/WebSocket 协议处理：路由、参数校验（Pydantic）、鉴权依赖、限流、统一响应、异常转 HTTP 状态码。 | 不写业务逻辑；通过`Depends(get_db)` / `Depends(require_scope(...))` 声明依赖；响应统一 `ApiResponse`。                                     |
| **业务层（Service）**            | `modules/*/service.py`                                                                    | 领域规则、事务边界、缓存失效、任务派发、跨模块编排。                                                | 可调用其他 module 的 service（如`item.service` 调 `message.service` 建会话）；失败抛 `BizError`；副作用（缓存/任务）尽量 try/except 降级。 |
| **数据访问层（Persistence）**    | `modules/*/models.py`、`common/models.py`、`core/database.py`、`core/sync_db.py`          | ORM 模型、表结构、异步 Session 管理、Alembic 迁移；Celery 侧用同步`sync_db`。                       | 模型只描述结构与关系；复杂查询用 SQLAlchemy`select` / 窗口函数；禁止在 models 里写业务规则。                                               |
| **基础设施层（Infrastructure）** | `core/*`（config / cache / redis / security / logging / storage / exceptions / response） | 与业务无关的技术能力：配置、缓存、Redis、安全、日志、存储、错误码。                                 | 单向依赖：基础设施**不依赖**业务模块；业务层通过接口使用。                                                                                 |
| **异步任务层（Tasks）**          | `tasks/*`                                                                                 | 邮件、站内通知、搜索索引同步等后台作业；`celery_app` 负责队列路由与重试。                           | 任务用`try/except` 保证自身不抛；调用方 `.delay()` 也需 try/except 降级（broker 不可达不阻塞主流程）。                                     |
| **集成层（Integration）**        | `search/client.py`、`modules/ai/*`、`core/storage.py`                                     | 封装外部系统：Meilisearch、OpenAI 兼容 AI、MinIO/本地存储。                                         | 必须提供**降级路径**（无搜索引擎走 SQL LIKE、AI 不可用走规则引擎、无 MinIO 走本地磁盘）。                                                  |

## 5. 依赖方向

单向依赖，无循环：

```
HTTP/WS 请求
   ↓
core/middleware.py  (限流 / trace id / 认证 / 管理员网关 / 指标)
   ↓
modules/*/router.py  ──Depends──> core/deps.py(require_scope) + core/database.py(get_db)
   ↓
modules/*/service.py ──调用──> modules/*/models.py + core/cache.py + core/redis.py
   │                    ──调用──> 其他 module 的 service.py（如 item → message）
   │                    ──派发──> tasks/*.delay()（try/except 降级）
   ↓
core/database.py (AsyncSession) ──> DB
core/search/client.py ──> Meilisearch（降级 SQL LIKE）
core/storage.py ──> MinIO（降级本地磁盘）
modules/ai/* ──> OpenAI 兼容 API（降级规则引擎）
```

**约束**：

- `core/*` 不 import 任何 `modules/*` 业务模块（基础设施单向被依赖）。
- `tasks/*` 不 import `router`，只被 `service` 以 `.delay()` 方式调用。
- 跨模块调用只允许 `service → service`，禁止 `router → 其他 router`。

## 6. 典型调用链路

### 6.1 通用 HTTP 请求链路

1. `core/middleware.py::GatewayMiddleware.dispatch`：生成/透传 `request_id` → bind 到日志上下文（trace id）。
2. 限流（Redis `INCR` + TTL，认证端点独立阈值）→ 超限返回 429（并埋点）。
3. 解析 `Authorization` → `core/security.py` 校验 JWT 与吊销状态。
4. 管理员路径校验 `X-Admin-Gateway` 短时令牌；校验失败返回 **404（隐藏后台存在性）**。
5. 路由到 `modules/*/router.py`，Pydantic 校验入参。
6. `service` 执行业务（事务 / 缓存 / 任务），返回领域对象。
7. `ApiResponse` 封装统一响应；`_record_metrics()` 记录 Prometheus 计数与延迟。

### 6.2 发布物品（含审核与索引同步）

`POST /api/items` → `item/router.py` → `item/service.py::create_item`

- 读 `item.review` 配置：`AppConfig`(DB) 优先，缺省回退 `school.yaml`；开启则状态为 `PENDING`，否则 `ON_SALE`。
- 写库 → `invalidate_namespace("items")` 失效列表缓存。
- `sync_item_search(item)`：仅「在售且未软删除」投递 `search_sync.sync_item`，否则 `delete_doc`；`.delay()` 异常仅记 warning。

### 6.3 创建交易（并发安全 + 通知）

`POST /api/items/{id}/trade` → `item/service.py::create_trade_session`

- `cas_item_status()`：一条 `UPDATE ... WHERE id=? AND status=ON_SALE` 做 CAS，抢占失败抛 409；同事务内建 `TradeSession` 与会话（部分唯一索引兜底）。
- 事务提交后：失效缓存 → `sync_item_search(item)` → `_notify_user(seller_id, ...)` 投递 `notify.send_notify`。
- 任一 `.delay()` 失败都不回滚业务，仅记日志。

### 6.4 内容发布预审

`share/teammate/job` 的 `create_*` → `ai/service.py::check_content_safety(db, text)`

- 读 `content.moderation` 配置（`admin/service.get_content_moderation_config`，DB 优先，默认关闭）。
- 关闭 → 直接放行；开启 → 调 `categorize_content()`；AI 不可用（开关关闭/无 Key）→ 降级 `_rule_moderation()` 规则引擎。
- 判定不安全 → 抛 `BizError(403)`，拒绝发布。

### 6.5 WebSocket 实时消息

`GET /ws?token=&since=` → `message/ws.py`

- 校验 token → 订阅 Redis 频道；多实例部署通过 Pub/Sub 广播。
- 客户端重连带 `since`，服务端用 **LocalSeq（ZSet 单调序号）** 补偿断线期间消息，保证不丢不重。
- Redis 不可用时 `redis_subscribe` 返回 `None`，WS 安静降级为单实例内推送。

## 7. 小结

- 分层清晰、依赖单向，模块化单体在**当前团队规模与交付节奏**下是最优解（后续若某域需要独立扩容，可按 `modules/` 边界拆分为服务）。
- 所有外部依赖（Redis / Meili / MinIO / AI）都设计了**降级路径**，这是本项目在“可本地零依赖开发 + 生产可渐进启用”之间的核心取舍。
- 本轮补齐了 metrics 埋点、搜索同步、内容预审与通知链路，四条此前“定义了但没真正用起来”的能力已全部闭环；`summary` 任务因零调用方被删除，避免死代码误导。
