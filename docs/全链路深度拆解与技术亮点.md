### 1.3 技术选型与可解释的取舍

| 选型 | 取舍理由（代码内有注释佐证） |
| --- | --- |
| **模块化单体** 而非微服务 | 单进程承载 REST + WS，无跨服务事务与网络开销；模块边界靠 `modules/<domain>/{models,schemas,service,router}.py` 强制隔离，未来可整目录拆出 |
| **SQLite ↔ PostgreSQL 双栈** | 开发零依赖（自动建表）、生产强一致（连接池 + 部分索引）；差异靠 `JsonList` 方言分支、连接池分支、SQLite 轻量迁移三处收敛 |
| **自建滑块验证码** 而非极验 | 自部署形态需离线可用；且 SVG 是明文（可从源码解析缺口坐标），故返回 **PNG 位图**（`auth/captcha.py:5-12`） |
| **bcrypt** 而非自研 | 标准库、常量时间比较，避免自造密码学 |
| **httpx 直调 OpenAI 兼容 `/chat/completions`** 而非 SDK | 减少依赖树与版本锁定风险，兼容 DeepSeek / Qwen / Kimi / GLM / Ollama（`ai/provider.py` 实现） |
| **Celery 结果后端 `disabled://`** | 注释直陈"发完即忘，从不 `.get()`"（`tasks/celery_app.py:51`），省掉一次 Redis 往返 |

## 2. 核心全链路深度拆解

### 链路一：账号注册与认证全链路

```
GET  /api/auth/captcha/config    前端据此决定要不要弹滑块
GET  /api/auth/captcha/slider    Pillow 渲染 PNG 位图（to_thread 不阻塞事件循环）
                                 → 缺口坐标只写 Redis，响应仅下发纵坐标 y
POST /api/auth/captcha/verify    三重判定 → 成功签发一次性票据
POST /api/auth/send-code         凭票据发送；票据消费即焚
POST /api/auth/email-register    域名白名单校验（四层配置）→ 注册即登录
      ↓ 签发双 Token
Authorization: Bearer <access 15min>  +  refresh <7d, jti 入库>
      ↓ access 过期
POST /api/auth/refresh          校验 jti 未吊销 → 轮换新对
POST /api/auth/logout           refresh 标记 revoked；access jti 进 Redis 黑名单至自然过期
```

**技术要点**

1. **滑块四重防线**（`auth/captcha.py`）
   - 缺口坐标**只存服务端 Redis**，响应只下发纵坐标 `y`（`:228`）——横坐标是唯一秘密。
   - 令牌**有限次**：失败累计 `tries`，达到 `captcha_max_attempts=3` 立即作废（`:300-301`）；成功**立即删除**（`:296`），杜绝"一次验证反复刷码"。
   - **三重反脚本判定**（`:287-292`）：位置容差 `6px` ＋ 拖动耗时 `≥80ms` 且 ≤TTL ＋ 轨迹形态校验 `_track_looks_human`（`:233-260`，要求 ≥6 个采样点、整体前进、单步 ≤120px、**步进集合去重后 >1 即拦截匀速直线**）。
   - **失败信息不分级**：坐标偏差与令牌失效统一返回同一句"滑块验证未通过"（`:271-272` 注释明示），不给攻击者调参反馈。
   - **CPU 密集隔离**：Pillow 渲染用 `asyncio.to_thread` 委派线程池（`:207-209`），注释详细解释了若直接在 `async def` 里跑会独占事件循环、在注册高峰叠加成 P99 抖动；并说明**不额外加信号量**是因为网关已对该路径限流 10/min，并发天然有界。

2. **双 Token + jti 黑名单**（`core/security.py`）：access 15min / refresh 7d（`:55-70`）；`revoke_token` 把 `jti` 写入 `jwt:blacklist:<jti>`，TTL = **剩余有效期**而非固定值（`:87-103`），避免黑名单无限膨胀。

3. **分级限流**（`core/middleware.py:124-164`）：全局 `120/min`，认证端点**独立严格** `10/min`，窗口 60s 固定计数。

4. **验证码存储双写**：Redis（主）+ `verification_codes` 表（留痕），TTL 300s、最大校验 5 次、发送间隔 60s（`core/config.py:141-144`）。

### 链路二：二手交易并发安全（本项目最硬核的一段）

**矛盾**：多买家同时对同一件在售物品发起交易，"先 SELECT 查状态 → 判断 → INSERT 建会话"的读-判-写分离会产生**一物双卖**。

```
POST /api/items/{id}/trade
  ↓ item/service.py:212-272 create_trade_session
  ↓ ① 条件 UPDATE 原子抢占（CAS）
      UPDATE items SET status=RESERVED WHERE id=? AND status=ON_SALE
      rowcount != 1 → 判负 → 409 CONFLICT
  ↓ ② 同事务内创建 TradeSession + 自动建会话
  ↓ ③ 捕获 IntegrityError → rollback → 转 409（索引兜底命中）
  ↓ ④ 状态机白名单 TRANSITIONS 校验合法迁移
```

**四层保障**

| 层 | 机制 | 证据 |
| --- | --- | --- |
| 应用层 | **条件 UPDATE（CAS）**：把读-判-写合成 1 条 SQL，`rowcount==1` 才算抢到 | `item/service.py:59-88` |
| 数据库层 | **部分唯一索引** `uq_trade_session_active_item`，`sqlite_where` + `postgresql_where` **双方言同时声明**，仅约束 `status IN (0,1)` 的活跃会话，终态可保留多条历史 | `item/models.py:61-69` |
| 事务层 | CAS 与建会话同事务，捕获 `IntegrityError` 后 `rollback` 转 409，**不做无界重试** | `item/service.py:257-265` |
| 状态层 | `TRANSITIONS` 白名单限定合法迁移，且允许 `RESERVED` 回退 `ON_SALE/SOLD/OFF_SHELF`，**避免物品卡死在中间态** | `item/statemachine.py:9-31` |

**为什么这四层值得写进简历**：它体现了"**并发正确性不靠单一银弹，而靠分层兜底**"的工程判断——乐观并发（CAS）解决绝大多数场景，唯一索引兜住极端竞态，状态机兜住业务非法迁移，事务兜住一致性。每一层都能单独回答面试官的追问。

### 链路三：即时消息实时链路

**矛盾**：会话列表需要同时返回「最后一条消息 + 未读数 + 对方资料」，朴素实现每会话 3 次查询，是典型 N+1。

**解法（O(3N+1) → 固定 4 条 SQL）** `message/service.py:51-151`：

1. 一次 JOIN 拉会话 + 参与者；
2. **窗口函数** `row_number().over(partition_by=conversation_id, order_by=created_at.desc())` 取 `rn==1` 得最后一条消息（`:87-93`）；
3. `GROUP BY conversation_id` 一次取全部会话未读数（`:96-107`）；
4. 批量 `IN` 查询对方用户资料，避免逐会话查（`:117-130`）。

代码注释直接写明了"旧实现 O(3N+1) → 新实现固定 ~4 条 SQL"，这是**可直接引用的量化证据**。

**实时推送**：`ConnectionManager.publish`（`message/ws.py:59-72`）先**本地直发**，再 `redis_publish(f"conv:{id}")` 跨实例广播；`_redis_listen` 订阅 `conv:*` 把其他实例的消息推给本实例连接（`:97-114`）。无 Redis 时退化为进程内直发。

**断线补偿——本项目设计最讲究的一处**（`message/seq.py`）：

- **为什么时间戳 `since` 不够**：模块 docstring（`:1-27`）完整论证——同一时间刻度内多条消息无法区分，用 `>` 会**丢消息**，放宽成 `>=` 会**重复推**。
- **解法**：Redis ZSet 作会话级**单调递增 LocalSeq**。序号由 `INCR` 分配（跨实例唯一、原子），`ZADD` 存消息体（score=seq），`ZREMRANGEBYRANK` 裁剪保留最近 **500 条**（`:41,:74`）。
- **补发区间为开区间 `(last_seq, +inf]`**（`:98`）——精确不重不漏。单次补发上限 **200 条**（`:88`）。
- **降级**：Redis 不可用时退化为进程内序号表（单实例语义正确），注释明说"功能退化，但连接不断"。
- 注释还特别说明：`INCR` 与 `ZADD` 之间**无需事务**，因为补发取的是区间而非连续序列，序号空洞不破坏语义。

### 链路四：管理后台纵深防御

```
POST /api/admin/discover  唯一公开端点：gateway_key → HMAC 短时令牌
     ↓
X-Admin-Gateway: <token>  其余 /api/admin/* 必带
     ↓ 无效 → HTTPException(404)  ← 注意是 404 不是 403
     ↓ 有效 → get_current_admin（校验 AdminUser 身份与 disabled）
     ↓      → require_scope("audit")（Scope 偏序 + 权限码映射）
     ↓      → 业务处理 → record_audit_log（独立会话提交）
```

1. **网关令牌**（`admin/gateway.py`）：`HMAC-SHA256(gateway_key|SECRET_KEY, "admin-gateway:{时间槽}")`，**无状态无需落库**，默认 3600s 轮换；校验时**同时接受当前槽与前一槽**（`:57`），覆盖轮换瞬间的时钟偏差。`hmac.compare_digest` 防时序攻击。
2. **404 而非 403 的设计意图**（`:65-67`）：让未授权扫描者以为接口不存在，隐藏管理端可达性。这是一个典型的"**安全靠信息不对称**"决策，面试时答出"为什么是 404"很加分。
3. **Scope 偏序 RBAC**（`core/deps.py:66-88`）：`read ⊂ write ⊂ admin` 偏序蕴含（`_SCOPE_IMPLIES`），权限码→作用域映射走最小权限；`get_principal`（`:130-184`）**同时查 User 与 AdminUser 双身份**，并用 `selectinload(AdminUser.role)` 规避异步 `MissingGreenlet`。
4. **管理员 seed 只增不减**（`admin/service.py:59-154`）：角色权限同步只做加法，注释解释"避免升级即丢权限导致升级即故障"；权限码必须登记，否则管理员会被自己的后台拒之门外。
5. **审计日志独立会话**（`audit/service.py:41-82`）：`record_audit_log` 内部吞掉所有异常（审计失败绝不影响业务），且用**独立的 `SessionLocal()`** 提交——因为登录失败等最需要留痕的事件往往伴随事务回滚，共用会话会导致日志一并丢失。`audit_logs` 只追加、不继承 `TimestampMixin`。

### 链路五：AI 能力链路（Agent 方向重点）

**矛盾**：AI 能力依赖外部 API，存在超时、配额、内容不合规三类不确定性，且无 Key 时不能拖垮主流程。

**实现**（`ai/service.py`）：

| 能力 | temperature | max_tokens | 特殊设计 |
| --- | --- | --- | --- |
| 校园洞察 `smart_campus_insights` | 0.8 | 256 | 带 `system_instruction` |
| 物品文案 `generate_item_description` | 0.7 | 384 | 带 `system_instruction` |
| 课程画像 `summarize_course_reviews` | 0.4 | 384 | 取 ≤50 条评价、每条截断 500 字 |
| 内容分类 `categorize_content` | **0.1** | 256 | **`json_mode=True`** |

- **温度分档本身就是 Prompt 工程判断**：创作类 0.8 保多样性，抽取/分类类 0.1 压确定性。
- **输出容错**（`:264-285`）：容忍模型输出带 ` ```json ` 围栏，校验 category 落在 9 个枚举内，否则归入"其他"——**不因模型输出格式抖动而报错**。
- **输入护栏**：`_MAX_CONTENT_LEN=3000` / `_MAX_REVIEW_TEXT_LEN=500` / `_MAX_INSIGHT_TOPIC_LEN=200`（`:43-45`），`reviewTexts` 入参上限 50 条（`schemas.py:43`）。
- **Key 隔离**：仅存后端（`AI_API_KEY` > `GEMINI_API_KEY` 兜底 > `school.yaml`），不下发浏览器。

### 链路六：配置治理与可观测性

**六层配置优先级**（实测链路）：

```
代码内 _DEFAULT_*  →  school.yaml  →  .env 环境变量  →  DB app_config 表  →  运行时热更新  →  前端兜底
```

- 敏感字段（admin 网关密钥 / MinIO / Meili）**`.env` 优先、空才回落 yaml**（`core/config.py:211-247`），避免仓库占位值顶掉生产强密码。
- **生产 fail-fast**：`validate_admin_security()`（`:267-342`）在非 debug 且强制网关时，对缺失/占位 `ADMIN_GATEWAY_KEY`、bootstrap 密码 <16 位、默认基础设施密钥（如 `minioadmin`）**直接 `SystemExit`** 拒绝带病上线。
- **热更新**（`core/config_reload.py`）：Redis Pub/Sub 频道 `config:reload`，监听器无限循环 + 异常自愈、30s 重试（`:49,:83-127`）；刷新采用**原地 `setattr`** 而非重建单例（`:75`），注释解释：若不原地刷新，数十个导入期绑定 `settings` 的引用会静默失效。
- **trace_id 穿透到 SQL**（`core/database.py:74-99`）：用 dialect 级 `do_execute` **监听器接管执行**注入 `/* trace_id=xxx */`。注释记录了关键踩坑——SQLAlchemy 2.0.30 下 `before_cursor_execute` 的返回值**不生效**（四种注册方式实测均无效），故改由监听器自己执行并返回 `True`。选注释作载体是因为它**对数据库透明（不改语义与执行计划）却原样出现在慢查询日志 / pg_stat_statements**。
- **注入防护**（`core/logging.py:33-45`）：`sanitize_trace_id` 用白名单正则 `[^A-Za-z0-9_.:-]` 收敛且限长 64——因为 `X-Request-ID` 是**不可信客户端输入**，不收敛就可能被构造成 `x */ DELETE FROM users; --` 闭合注释注入 SQL。

### 3.3 "四层分类配置"模式（item/job/share/teammate 共用）

以分类为例，同一套解析链复用到 4 个业务域（`admin/service.py:384-481`，表驱动 `_CATEGORY_SPECS`）：

```
yaml 默认 → env 覆盖 → DB app_config(key=item.categories) 优先 → 公开端点下发
                                    ↓
                      normalize_category：非法/空分类收敛到"其他"
```

关键决策：归一化时**选"收敛到默认"而非"拒绝发布"**（`:458-481`）——避免运营后台改分类后，用户历史内容突然发布失败。DB 侧限制单条分类 ≤20 字符、总数 ≤30 条（`:302-303`）。

## 6. 面试高频追问预案

| 追问 | 应答要点 |
| --- | --- |
| 为什么不用分布式锁（Redlock）而用 CAS？ | CAS 把一致性交给数据库的单行原子性，无额外组件、无锁超时与续期问题；唯一索引作二次兜底，比引入 Redlock 的运维成本低一个数量级 |
| CAS 失败为什么要直接 409 而不是重试？ | 抢购场景下重试只会放大冲突；直接失败让用户刷新拿到最新状态，语义更清晰，也避免请求堆积 |
| 部分唯一索引为什么 SQLite/PG 要各写一份？ | SQLAlchemy 的 `Index` 支持 `sqlite_where` / `postgresql_where` 方言参数，按方言择一生效，从而一套模型同时支持开发 SQLite 与生产 PG |
| 为什么断线补偿用序号不用时间戳？ | 引用 `message/seq.py` 的论证：同刻度多消息无法区分，`>` 丢消息、`>=` 重复推；单调序号的区间 `(N,+inf]` 精确不重不漏 |
| 管理端为什么返回 404 不是 403？ | 403 确认了资源存在，等于给扫描者发地图；404 让探测者以为端点不存在，是廉价且有效的存在性隐藏 |
| 滑块验证码为什么不用第三方？ | 自部署需离线可用、无外网依赖；且 SVG 明文会泄露缺口坐标，故返回 PNG 位图 |
| 图像渲染为什么要 `to_thread`？ | Pillow 绘制与 PNG 编码是同步 CPU 密集，直接在 `async def` 里跑会独占事件循环，注册高峰叠加成 P99 抖动 |
| 为什么要自己注入 trace_id 到 SQL？ | 注释是唯一对数据库透明却能原样出现在慢查询日志的载体，能把 Nginx → 应用 → 慢 SQL 串成一条线 |
| 配置热更新为什么原地 setattr？ | 数十个模块在导入期就绑定了 `settings` 引用，重建单例会让这些引用静默指向旧对象 |
| 无 Redis 时系统还能用吗？能用到什么程度？ | 能。Redis 退化为内存 dict（限流/验证码/缓存语义对齐）、MinIO 退化为本地盘、Meili 退化为 SQL LIKE、WS 广播退化为进程内直发——功能退化但服务不中断 |
