### 1.2 两个状态机

**物品状态**（`common/enums.py:22-33`）：

```
PENDING(4) 待审核 ──审核通过──> ON_SALE(0) 在售
     │                            │
  审核拒绝                    发起交易(CAS)
     ↓                            ↓
OFF_SHELF(1) 下架 <──取消交易── RESERVED(3) 已预订
     ↑                            │
     └────卖家手动下架────────────┤
                              确认成交(CAS)
                                  ↓
                            SOLD(2) 已售（终态）
```

**交易会话状态**（`common/enums.py:36-42`）：

```
PENDING(0) / IN_PROGRESS(1)  ──完成──>  COMPLETED(2)
                             ──取消──>  CANCELLED(3)
```

终态（COMPLETED / CANCELLED）不参与"一物一活跃会话"的唯一约束。

```
  │   ├─ 新建 TradeSession(PENDING)             service.py:323-330
  │   ├─ flush() 让唯一索引立刻可见              service.py:330
  │   ├─ 新建 trade 类型聊天会话                  service.py:332-341
  │   └─ commit()                               service.py:342
  │ 【事务结束】
  │
  ├─ 事务外副作用（best-effort）
  │   ├─ 失效物品列表缓存                        service.py:356
  │   ├─ 同步搜索索引                            service.py:357
  │   └─ 发站内通知给卖家                        service.py:358-362

  A. POST /api/items/trades/{id}/complete        router.py:157-165
     → 会话 CAS 至 COMPLETED + 物品 CAS 至 SOLD（同一事务） service.py:386-416
  B. POST /api/items/trades/{id}/cancel          router.py:168-176

```

### 1.4 为什么要设计"预留"这一步

`service.py:367-373` 有一段重要的历史注释：早期 `TradeSession` 创建后状态永不变更，卖家把 `RESERVED` 物品重新上架后，部分唯一索引让所有新抢占都 409，物品和旧会话**互相锁死**。于是补了 `complete/cancel` 两个出口。

这段历史解释了后面第 6 节"释放链路"的由来：**释放不是锦上添花，而是这个状态机必需的逃生通道**。

## 2. 事务：这个项目是怎么涉及的

### 2.1 新手先理解：什么是事务

事务（Transaction）就是**一组数据库操作，要么全做，要么全不做**。经典例子是转账：

- A 账户扣 100
- B 账户加 100

如果第一步成功、第二步失败，钱就凭空消失了。事务保证这两步是一个不可分割的整体：中途出错就 `ROLLBACK`（全部撤销），全部成功才 `COMMIT`（真正落盘）。

事务的四个特性（ACID）：

| 特性 | 含义 | 在本项目中的体现 |
|---|---|---|
| **A** 原子性 | 全做或全不做 | CAS + 建会话 + 建聊天在同一事务，任一失败整体回滚（`service.py:313-314`） |
| **C** 一致性 | 数据满足业务规则 | 不会出现"物品是 RESERVED 但没有任何活跃交易会话" |
| **I** 隔离性 | 并发事务互不干扰 | 靠 CAS 单条 UPDATE 实现，**没有**配置隔离级别或行锁 |
| **D** 持久性 | 提交后不丢失 | `commit()` 落盘；但外部副作用（通知/搜索）不在此保障内 |

三个必须分清的动作：

- **`flush()`**：把内存中的 ORM 改动发成 SQL，但**还在事务里，可被回滚**。目的是让后续 SQL（比如 CAS、唯一索引检查）能看到这批数据。
- **`commit()`**：**提交事务**，真正落盘，不可回滚。
- **`rollback()`**：**撤销事务**里所有未提交的改动。

> 新手最容易踩的坑：以为 `flush()` 就是保存。不是！`flush()` 之后另一个事务看不到你的数据，而且出错还能回滚。

### 2.2 项目的事务基础设施

**Session 工厂** — `core/database.py:47-52`：

```python
SessionLocal = async_sessionmaker(
    bind=engine,
    class_=AsyncSession,
    expire_on_commit=False,
    autoflush=False,
)
```

- `expire_on_commit=False`：提交后对象属性仍可读，不会触发额外的惰性查询。
- `autoflush=False`：**关键配置**。ORM 改动不会自动刷出，所以凡是"先改 ORM 再 CAS"的地方都必须手动 `flush()`（`item/service.py:268`、`admin/service.py:840`）。

**请求级 Session** — `core/database.py:102-109`：

```python
async def get_db():
    async with SessionLocal() as session:
        try:
            yield session
        except Exception:
            await session.rollback()
            raise
```

注意两个事实：

1. **成功路径不 commit**。提交完全由各 service 显式 `db.commit()` 负责，没有隐式提交。
2. **异常路径兜底 rollback**。这是最后一道防线：如果 service 抛异常但忘记回滚，这里会兜住。

> 结构性风险：未来如果某个写函数改了 ORM 却忘记 `commit()`，请求会正常返回 200，但数据静默丢失。当前代码里所有写函数都显式 commit，所以这不是现存 bug，而是设计上的取舍。

**引擎配置** — `core/database.py:23-45`：

- 开发默认 SQLite（`config.py:49-53`，`sqlite+aiosqlite:///./dev.db`），生产用 PostgreSQL。
- `create_async_engine(...)` 里**没有传 `isolation_level`**，全库也没有 `BEGIN IMMEDIATE` 或 `with_for_update()`。隔离行为完全交给驱动默认值。
- `engine.begin()` 只用于 DDL/建表（`database.py:296` 等），**不参与业务事务**。

**Celery 同步引擎** — `core/sync_db.py:23-49`：worker 是同步进程，用 `psycopg2`/内置 sqlite 驱动另开一条同步 DB 通道。但它不封装 commit/rollback，且当前业务任务（邮件、通知、搜索同步）**根本不访问数据库**，只在 `scripts/rebuild_search_index.py:26,46-48` 用到了。

### 2.4 事务与 CAS：为什么必须放在同一个事务

`item/service.py:306-314` 的注释是核心答案：

- 如果"抢占状态"和"创建会话"分成两个事务，中间就可能失败：物品已经 `RESERVED`，但会话没建出来——这叫**僵尸状态**。由于没有活跃会话，也没有任何出口，`RESERVED` 会一直卡住。
- 放在同一个事务后：任一步失败整体回滚，物品回到 `ON_SALE`，不会留下半成品。

`flush()` 在这里还有一个具体作用（`:330`）：让新建的 `TradeSession` 在 `create_conversation` 之前就被数据库看到，使部分唯一索引能及时生效。`rowcount` 的判断（`cas_item_status :147-156`）依赖同一事务内数据库返回的影响行数——这行 UPDATE 是整个并发控制的原子操作。

### 2.5 事务与网络副作用的顺序

这是理解"数据一致性边界"的关键。项目遵循一个清晰模式：

```
【事务内】只做数据库操作
    CAS → flush → 建会话 → commit
【事务外】才做外部副作用
    缓存失效 → 搜索索引同步 → 站内通知
```

commit 后执行的三类副作用：

| 副作用 | 实现 | 位置 |
|---|---|---|
| 缓存失效 | `invalidate_namespace("items")`，Redis 版本号 INCR，无 Redis 时内存降级 | `core/cache.py:136-143`；`item/service.py:119,274,289,356,414,449` |
| 搜索同步 | `search_sync.index_item/remove_item`（线程池 `.delay()`）+ `sync_item_search`（直接 `.delay()`） | `search/sync.py:31-47,87-106`；`item/service.py:121,276,290` 与 `:122,277,357` |
| 站内通知 | `notify_tasks.send_notify.delay(...)` | `item/service.py:42-47`，触发点 `:358` |

**失败时会怎样？**

- 这些 `.delay()` 都是在 **commit 之后**调用的。broker 不可达时 `.delay()` 快速失败（约 1 秒，`tasks/celery_app.py:43-51,64-81`），但调用方只记 warning 就丢弃（`item/service.py:46-47,81-82`、`search/sync.py:41-45`）。
- 结果：DB 已经提交（交易确实创建了），但通知或索引永久缺失。**没有 outbox 表、没有补偿任务**。
- 通知任务自身有 3 次重试（`tasks/notify.py:12,29-31`），但那是**入队成功之后**的重试；入队失败那一下的消息直接丢了。
- 搜索索引有兜底：查询侧保留 DB LIKE 降级（`search/sync.py:9-12`），所以索引缺失不至于查不到数据。
- 缓存失效在 `redis_incr` 内部降级，不会回滚业务。

一句话概括项目的一致性模型：**数据库内部强一致 + 外部系统 best-effort 最终一致**。外部失败不会制造 DB 脏数据，但会制造"交易已创建、卖家没收到通知"这类业务可见的不一致。这就引出了第 6 节"对账"的概念——只不过本项目没有实现对账。

### 2.6 失败路径：rollback 与吞异常

**rollback 位置**（`backend/app/` 共约 13 处）：

- `core/database.py:108`：所有异常的兜底回滚。
- `item/service.py:346`：唯一索引冲突 → 409。
- `item/service.py:350`：其他异常 → 原样上抛（由 `get_db` 兜底）。
- 其他模块同类模式：`user/service.py:141`（重复收藏**吞掉，视为成功**）、`teammate/service.py:106`、`job/service.py:93`、`report/service.py:34`、`course/service.py:61,93`、`canteen/service.py:176`、`auth/service.py:215,444`。
- `ai/service.py:348,802`：AI 日志写入失败后回滚，连回滚自身的异常也吞掉。

**异常如何变成 HTTP 响应**：`BizError` 由 `core/exceptions.py:48-52` 统一包装成 **HTTP 200 + body.code=40900**（冲突）或 42200（校验失败）等业务码，而不是标准的 4xx 状态码。测试里断言的是 `code == 40900`。

**吞异常只记日志的地方**（学习"有意为之的降级"）：

- `cancel_trade` 的物品释放失败：`item/service.py:438-446`，只记 info，**取消本身照常提交**。这意味着物品可能仍留在 `RESERVED`，部分唯一索引继续挡新交易——见第 6 节的语义缺口。
- 通知派发失败 `service.py:46-47`、搜索派发失败 `:81-82,292-295`、审计写失败 `audit/service.py:80-85`、索引迁移失败 `database.py:287-291`。

注意区分：**吞掉的是"入队/建索引/记日志"这类副作用**，任务体本身失败是会重试的（`tasks/notify.py:29-31`、`tasks/email.py:76-78`、`tasks/search_sync.py:12-41`）。

## 3. CAS 与并发读写冲突

### 3.1 什么是 CAS

CAS = Compare-And-Swap（比较并交换）。通俗说：**"只有当当前值还是我刚才看到的值时，才把它改成新值"**。

数据库里实现 CAS 只需要一条带条件的 UPDATE：

```sql
UPDATE items SET status = 3 WHERE id = ? AND status = 0;
```

- 返回"影响 1 行" → 抢占成功，你就是那个把状态从 0 改成 3 的人。
- 返回"影响 0 行" → 失败，说明在你执行之前状态已经被别人改过了。

### 3.2 为什么需要它：check-then-act 竞态

新手常写这样的代码：

```python
item = await get_item(db, item_id)
if item.status == ON_SALE:      # 读
    item.status = RESERVED      # 写
    await db.add(trade_session)
```

问题在于"读"和"写"之间有时间窗。两个买家同时读到 `ON_SALE`，于是两个人都通过检查，各自建了一个会话——**同一件商品被卖了两次**。这就是经典的 check-then-act 竞态（也叫 TOCTOU）。

项目注释在 `item/service.py:306-314` 详细解释了这一点。CAS 把"判断"和"写入"合成一条 UPDATE，由数据库保证原子性：只有一个请求的 `rowcount` 会是 1。

### 3.3 项目里的三处关键 CAS

1. **发起交易**：`item/service.py:303-322`
   - 先做普通校验（不能自交易、必须 `ON_SALE`），再用 `cas_item_status` 原子 `ON_SALE → RESERVED`。
   - 复用同一个 `cas_item_status` 函数（`:127-156`），失败抛 `ErrorCode.CONFLICT`（409）。

2. **确认成交**：`item/service.py:386-416`
   - 会话 CAS：只把 `PENDING/IN_PROGRESS` 改成 `COMPLETED`（`:393-402`）。
   - 物品 CAS：只把 `RESERVED` 改成 `SOLD`（`:405-411`）。
   - **两个 CAS 在同一事务**（`:412` 才 commit）。如果物品已被卖家重新上架（不是 `RESERVED`），整体失败，避免"交易完成但物品在别人手里"的错位。

3. **取消交易**：`item/service.py:419-451`
   - 会话 CAS：`PENDING/IN_PROGRESS → CANCELLED`（`:426-435`）。
   - 物品 CAS：`RESERVED → ON_SALE`（`:438-441`），但失败被吞掉（见 2.6 节）。

**通用 CAS 函数**：`item/service.py:127-156`，注释说明"SQLite 与 PostgreSQL 下语义一致，故作为主实现，无需按数据库分支"（`:145`）。

**状态机白名单**：`item/statemachine.py:8-31` 是另一层防护。它校验"这个流转在业务上是否合法"，但它是**应用层校验**，不保证并发安全；CAS 才是并发安全的保证。两者职责不同，不要混淆。

### 3.4 并发控制的第二道防线：部分唯一索引

`item/models.py:61-69`：

```python
Index(
    "uq_trade_session_active_item",
    "item_id",
    unique=True,
    sqlite_where=text("status IN (0, 1)"),
    postgresql_where=text("status IN (0, 1)"),
)
```

含义：**同一个 `item_id`，处于活跃状态（0/1）的会话最多只能有一条**。终态会话不受约束，所以同一物品可以保留多条历史成交记录。

这叫**部分唯一索引**（Partial Index）：只对满足 WHERE 条件的行建立唯一约束。它兜底的极端场景是"CAS 判定与索引不一致"（例如管理员手工改状态），此时会触发 `IntegrityError`，被 `service.py:343-348` 捕获 → `rollback()` → 转 409。

老库的索引补齐在 `core/database.py:196-207,275-291`，幂等设计（同名索引跳过），建索引失败只记 error 不阻断启动。Alembic 版本在 `alembic/versions/0002_campus_config.py:97-104`。

### 3.5 明确没有的并发机制

| 机制 | 状态 |
|---|---|
| `SELECT ... FOR UPDATE` / `with_for_update()` | 无（全库检索无匹配） |
| `isolation_level` 配置 | 无，用驱动默认值 |
| 乐观锁 `version` 列 | 无 |
| Redis 分布式锁参与交易 | 无（`celery_app.py` 的 Redis Lock 只是 kombu 兼容层） |
| 数据库冲突自动重试循环 | 无，冲突直接转 409 |
| 真正并行的 N 抢 1 压测 | 无（见第 9 节） |

## 4. 幂等性：同一个业务意图被执行多次

### 4.1 什么是幂等

幂等（Idempotent）指：**同一个操作执行一次和执行多次，对系统的最终影响相同**。

HTTP 语义里，GET/PUT/DELETE 天然幂等（查一万次结果一样；PUT 同一个资源到同一个值结果一样；DELETE 一次和多次都是"不存在"）；而 POST 通常不幂等（每次都新建一条）。

放到交易场景，幂等要回答的问题是：

- 用户手抖点了两次"确认完成"，会怎样？
- 网络超时后客户端自动重试，服务端会不会重复扣费/重复建单？

### 4.2 本项目怎么处理的

项目**没有业务幂等键**，而是靠**状态机把重复操作变成冲突**：

| 重复场景 | 防护机制 | 结果 |
|---|---|---|
| 重复点"我想要" | 物品已 `RESERVED`，CAS 期望 `ON_SALE` 失败 | 409（`service.py:303-322`） |
| 重复 complete | 会话状态已不是 `PENDING/IN_PROGRESS`，`rowcount=0` | 409 "该交易已完成或已取消"（`:403-404`） |
| 重复 cancel | 同上 | 409（`:436-437`） |
| 并发建出两个会话 | 部分唯一索引 + `IntegrityError` | 409（`:343-348`） |
| 前端重复点击 | `actionLoading` + `disabled` | 按钮禁用，请求期间不可再点（`MarketDetail.tsx:22,66,80,281-288`） |

### 4.3 注意：这不是严格意义的幂等

重复调用 `complete/cancel` 返回的是 **409 错误**，而不是"返回第一次的结果"。严格幂等要求客户端重试能拿到相同的成功结果；这里更准确的说法是**"重复执行被安全地拒绝，不会产生重复副作用"**。对撮合型业务这通常是可接受的——用户看到"已处理"的提示即可。

### 4.4 容易误认的东西

`X-Request-ID`（`core/middleware.py:144-147,249`）只是链路追踪 ID，用于串联日志，**不是幂等键**。`audit/service.py:58-77` 只是把它写进审计日志。项目没有 `Idempotency-Key` 请求头、没有请求去重表。

## 5. 防超卖：三种库存模式的代价辨析

### 5.1 问题背景

"超卖"指卖出的数量超过实际可用数量。电商里是"库存 1 件卖出 10 单"；在这个项目里，等价问题是**同一件二手物品被多个买家同时抢到**。

处理思路有三种，代价完全不同：

### 5.2 模式一：预占（先锁后付）—— 本项目采用

流程：下单时先把库存标记为"已预留"，支付/确认后再转成"已售"；超时未支付则释放回"在售"。

```
ON_SALE --抢购--> RESERVED --确认--> SOLD
                     |
                  取消/超时
                     ↓
                  ON_SALE
```

项目里的对应实现：

- 状态定义：`common/enums.py:29-33` 的 `RESERVED=3`。
- 抢占：`item/service.py:306-322` CAS `ON_SALE → RESERVED`。
- 出口：`item/statemachine.py:10-16` 允许 `RESERVED → ON_SALE/SOLD/OFF_SHELF`。
- 成交：`item/service.py:405-411` CAS `RESERVED → SOLD`。
- 取消：`item/service.py:438-441` CAS `RESERVED → ON_SALE`。

**代价**：
- 优点：用户感知公平（谁先抢到谁有），不会超卖，库存状态清晰。
- 缺点：**必须实现释放链路**，否则预占会永久卡死——这正是项目历史上踩过的坑（见 1.4 节）。而且本项目目前只有手动取消，**没有超时自动释放**。

### 5.3 模式二：扣减（付了才扣）

流程：支付成功时才真正扣减库存。下单阶段不占库存。

**代价**：
- 优点：没有"预留卡死"问题，逻辑简单。
- 缺点：高峰期可能出现"用户付了钱才发现没货"，需要退款补偿；并发下要靠 `stock > 0` 的条件扣减（`UPDATE ... SET stock=stock-1 WHERE stock>0`）兜底。
- 本项目**没有采用**：`item/models.py:23` 只有一个 `status` 字段，没有 `stock`/`quantity` 数量字段（二手物品一件就是一件，天然是单值状态）。

### 5.4 模式三：事后补偿（先卖后补）

流程：先放行成交，事后通过异步任务检查超额部分，再自动退款/赔付。

**代价**：
- 优点：下单链路最快，吞吐量最高。
- 缺点：用户体验差（可能买到air），需要完整的补偿和对账系统，实现复杂度最高。
- 本项目**没有采用**：没有任何超额成交后的补偿/赔付流程。

### 5.5 三种模式对比

| 维度 | 预占（本项目） | 扣减 | 事后补偿 |
|---|---|---|---|
| 防超卖时机 | 下单时锁 | 支付时扣 | 成交后纠偏 |
| 需要库存字段 | 否（用状态位） | 是 | 是 |
| 必须有释放链路 | **是** | 否 | 否 |
| 必须有对账 | 建议有 | 建议有 | **必须有** |
| 用户体验 | 公平、可能需等待释放 | 可能付款后无货 | 可能买到air |
| 实现复杂度 | 中 | 低 | 高 |

## 6. 释放链路与对账

### 6.1 什么是释放链路

预占模式下，被锁住的资源必须有办法回到可卖状态，否则就是"死锁"。完整的释放链路通常包括：

1. **用户主动取消**（本项目有）
2. **超时自动释放**：预占超过 N 分钟未确认，系统自动回退（本项目没有）
3. **兜底修复**：通过定时任务扫描异常状态并修正（本项目没有）

### 6.2 项目里已有的释放出口

- HTTP 端点：`item/router.py:168-176` `POST /api/items/trades/{id}/cancel`。
- 实现：`item/service.py:419-451`。
- 状态机允许 `RESERVED → ON_SALE/OFF_SHELF`：`item/statemachine.py:12-15`。
- 设计动机注释：`item/service.py:367-373`、`router.py:152-155`。
- 参与者校验：只有买卖双方能取消（`service.py:381-383`）。

### 6.3 现有释放的语义缺口

`cancel_trade` 里，物品 CAS 失败被吞掉（`:438-446`）：

```python
try:
    await cas_item_status(db, str(trade.item_id), RESERVED, ON_SALE)
except BizError:
    _logger.info("trade_cancel_item_not_reserved", ...)
```

也就是说：会话确实变成了 `CANCELLED`，但物品可能还停在 `RESERVED`。此时部分唯一索引已经不再约束这个终态会话（因为状态不在 `IN (0,1)`），但物品看起来还是"已预订"，新交易无法发起——**与函数注释 `:419-423` 承诺的"物品释放回 ON_SALE"存在落差**。这是有意为之的"尽力而为"设计：取消操作本身必须成功，不能因为物品状态异常而连取消都做不了。

### 6.4 什么是对账

对账（Reconciliation）指：**定期比较两个本应一致的数据源，找出并修复不一致**。在这个场景里要检查的典型异常是：

- 物品是 `RESERVED`，但没有任何活跃交易会话（僵尸预留）
- 有活跃交易会话，但物品不是 `RESERVED`
- 交易会话是终态，但物品仍停在 `RESERVED`

**本项目没有实现任何对账逻辑**，也没有 Celery Beat 定时任务（`tasks/celery_app.py:54-99` 只有队列路由和重试配置，`tasks/__init__.py:8-10` 只注册 email/notify/search_sync 三类任务）。 RESERVED 只能靠人工 `cancel_trade` 出口。

理解这一点很重要：第 2.5 节说过，通知/索引这类外部副作用是 fire-and-forget；对账本应是它们的补偿手段，但本项目没有，所以那些副作用一旦入队失败就永久缺失。

## 11. 术语表

| 术语 | 一句话解释 |
|---|---|
| **事务 Transaction** | 一组 DB 操作，全做或全不做 |
| **ACID** | 原子性、一致性、隔离性、持久性 |
| **commit / rollback** | 提交事务（落盘）/ 撤销事务 |
| **flush** | 把 ORM 改动发成 SQL，但仍在事务内、可回滚 |
| **autoflush=False** | 关闭自动刷出，CAS 前必须手动 `flush()` |
| **CAS** | `UPDATE ... WHERE status=旧值`，用影响行数判断是否抢占成功 |
| **rowcount** | SQL 影响的行数，CAS 成败的判据 |
| **竞态 check-then-act** | 读和写之间有时间窗，并发下两个请求都通过检查 |
| **部分唯一索引** | 只对满足 WHERE 条件的行建唯一约束（如 `status IN (0,1)`） |
| **IntegrityError** | 违反唯一约束等完整性限制时数据库抛的异常 |
| **幂等** | 执行一次和执行多次效果相同 |
| **预占 / RESERVED** | 先锁库存再确认的模式（本项目采用） |
| **超卖** | 卖出数量超过实际可用数量 |
| **释放链路** | 把预占资源退回可卖状态的路径 |
| **对账 Reconciliation** | 定期比对并修复本应一致的数据 |
| **Outbox** | 在业务表里同事务记录待发送消息，由异步任务可靠投递（本项目未实现） |
| **隔离级别** | 事务之间可见性的规则（读未提交/读已提交/可重复读/串行化），本项目用驱动默认值 |
| **行锁 `SELECT FOR UPDATE`** | 显式锁住读到的行，防止并发修改，本项目未使用 |
| **BizError / 40900** | 项目自定义业务异常，统一包装成 HTTP 200 + body.code 返回 |
| **Celery `.delay()`** | 把任务投递到 broker 异步执行；broker 不可达时快速失败 |
| **Redis Pub/Sub** | 跨进程广播消息的机制，用于 IM 消息分发 |

## 12. 补充：后端横切关注点

前面 1～7 节是**交易正确性**主线：会不会算错、超卖、重复执行。后端处理一笔交易还需要一批**横切关注点**——它们不直接决定"会不会超卖"，但决定"会不会被越权操作、被刷、查不到、出问题说不清"。本节按项目实际代码核对后列出。

### 12.1 安全与权限

## 13. 唯一索引：概念与项目中的应用

唯一索引贯穿了本项目的多个模块，但它最精彩的用法是第 3.4 节提到的**部分唯一索引**——用来兜底"一物多卖"。本节把概念讲清楚，再把项目里所有应用点列全。

### 13.1 概念入门

**索引（Index）** 是数据库为加速查询维护的额外数据结构。可以类比书的目录：没有目录要一页页翻（全表扫描），有目录可以直接定位。

**唯一索引（Unique Index）** 在加速查询之外，还附加一条硬规则：**被索引的列（或列组合）的值不能重复**。如果插入第二条相同的值，数据库直接抛 `IntegrityError`（完整性约束违反）。

普通索引 vs 唯一索引：

| | 普通索引 | 唯一索引 |
|---|---|---|
| 加速查询 | 是 | 是 |
| 禁止重复值 | 否 | **是** |
| 写操作开销 | 中 | 略高（每次写入都要检查重复） |
| 典型用途 | `status`、`title`、`created_at` 等筛选字段 | 用户名、邮箱、"同一用户只能评价一次"等业务唯一性 |

**组合唯一索引**：唯一性约束在多个列的组合上。例如 `(user_id, item_id)` 唯一，意思是"同一个用户可以收藏很多物品，同一个物品可以被很多人收藏，但同一个用户对同一个物品只能收藏一次"。

**部分唯一索引（Partial Unique Index）**：只对**满足 WHERE 条件的行**施加唯一约束。这是本项目最关键的用法：

```sql
CREATE UNIQUE INDEX uq_trade_session_active_item
ON trade_sessions (item_id) WHERE status IN (0, 1);
```

含义：同一个 `item_id` 只允许一条"进行中"的会话（状态 0 或 1）。已结束的会话（状态 2/3）不受约束，所以历史成交记录可以保留很多条。如果不用部分索引、直接对 `item_id` 建普通唯一索引，那这个物品这辈子只能有一笔交易记录——显然不对。

**为什么唯一索引是并发的最后一道防线**：应用层可以先 `SELECT` 检查"有没有重复"，但"检查"和"插入"之间有时间窗（check-then-act，见 3.2 节），两个并发请求可能都通过检查。唯一索引由数据库在写入时强制执行，**没有这个时间窗**——哪怕两个请求同时通过应用层检查，数据库也只会让一个插入成功。所以项目的模式是：**应用层预检改善体验 + 唯一索引兜底保证正确**。

### 13.3 部分唯一索引深入：`trade_sessions`

这是整个项目里唯一的部分唯一索引，也是防超卖双保险的第二层。

**模型定义** — `item/models.py:50-69`：

```python
__table_args__ = (
    Index(
        "uq_trade_session_active_item",
        "item_id",
        unique=True,
        sqlite_where=text("status IN (0, 1)"),
        postgresql_where=text("status IN (0, 1)"),
    ),
)
```

模型注释 `models.py:53-56` 解释了设计：服务层先用 CAS 抢占物品，这里再补一层唯一索引兜底——同一物品同时最多一个"进行中"会话；终态会话不参与约束，历史成交记录仍可保留多条。

**防超卖双保险的分工**：

1. 第一层 CAS（`item/service.py:127-156,316-322`）：正常路径，把 `ON_SALE → RESERVED`，抢不到的直接 409。
2. 第二层唯一索引（本索引）：极端情况下兜底——比如管理员手工改状态导致 CAS 判定与索引不一致，此时 `IntegrityError` 被 `service.py:343-348` 捕获 → `rollback()` → 409。

**方言差异处理**：SQLite 和 PostgreSQL 都支持 `CREATE UNIQUE INDEX ... WHERE` 语法。项目在三处写了相同的裸 SQL，保证两端一致：

- 模型层：`sqlite_where` + `postgresql_where` 同时声明（`item/models.py:66-67`），SQLAlchemy 按方言生成 DDL。
- Alembic：`alembic/versions/0002_campus_config.py:97-104`，注释 `:99` 说明历史上按数据库分支的两段代码完全相同，已合并。
- SQLite 轻量迁移：`core/database.py:204-205`。

### 13.4 迁移：老库怎么补上唯一索引

**问题**：SQLAlchemy `create_all` 只给**新建表**建索引，已经存在的老表不会补。如果老库缺这个唯一索引，并发安全就只剩应用层 CAS 单防。

**SQLite 轻量迁移** — `core/database.py:196-207,275-291`：

- `_SQLITE_INDEX_MIGRATIONS`（`:200-255`）列出 7 个命名唯一索引的 CREATE 语句：
  - `trade_sessions` `uq_trade_session_active_item`（`:201-207`）
  - `course_reviews` `uq_course_review_user`（`:210-216`）
  - `canteen_reviews` `uq_canteen_review_user`（`:217-223`）
  - `reports` `uq_report_reporter_target`（`:225-231`）
  - `job_applications` `uq_job_application`（`:233-239`）
  - `team_members` `uq_team_member`（`:240-246`）
  - `user_favorites` `uq_user_favorite`（`:248-254`）
- 执行逻辑（`:275-291`）：`PRAGMA index_list(table)` 拿到已有索引，同名则 `continue`（`:282-283`）——**幂等**；建索引失败只 `_logger.error("db_index_migration_failed")`，**不阻断启动**（`:287-291`）。
- 为什么容忍失败：老数据里若已存在重复的活跃会话，唯一索引建不起来。注释 `:288-290` 说明——一处脏数据让整站起不来，代价远大于索引缺失。

**Alembic** — `alembic/versions/0001_initial.py:27-29` 用 `create_all` 做快照基线（隐式建所有索引）；`0002_campus_config.py:97-104` 是唯一显式创建部分唯一索引的版本，用 `_indexes_of()` 探测后执行裸 SQL（`:47-48,100`），downgrade 在 `:111` DROP。

**启动链路**：`main.py:54` lifespan → `init_models(Base)`（`core/database.py:294-300`）→ `create_all` → 轻量迁移。

### 13.5 冲突发生时 service 怎么处理

数据库抛 `IntegrityError` 后，项目的处理策略有两种：

**策略一：转 40900（主流）**

| 唯一约束 | 捕获位置 | 业务语义 |
|---|---|---|
| `uq_job_application` | `job/service.py:89-94` | 40900 "已申请过该岗位" |
| `uq_team_member` | `teammate/service.py:102-107` | 40900 "已在团队中" |
| `uq_trade_session_active_item` | `item/service.py:343-348` | 40900 "该物品已有进行中的交易，无法重复发起" |
| `uq_course_review_user` | `course/service.py:88-94` | 40900 "您已评价过该课程" |
| `uq_canteen_review_user` | `canteen/service.py:172-177` | 40900 "您已评价过该菜品" |
| `uq_report_reporter_target` | `report/service.py:29-35` | 40900 "请勿重复提交相同举报" |
| `courses.code` | `course/service.py:57-62` | 40900 "课程代码已存在" |
| `users.username/email/phone` | `auth/service.py:210-216` | 40900 "用户名或邮箱已被注册"（预检在 `:184-205`） |
| OAuth 同名冲突 | `auth/service.py:440-445` | 40900 "登录初始化冲突" |

40900 定义在 `core/exceptions.py:35`，统一包装成 HTTP 200 + body.code（`:48-52`）。

**策略二：吞掉视为成功（特例）**

`user/service.py:137-143` 的重复收藏：捕获 `IntegrityError` → `rollback()` → 记日志 `favorite_duplicate_ignored` → **正常返回**。`user/router.py:107` 注释明确"重复收藏不报错"。这是典型的**幂等语义**——用户点两次收藏，结果都是"已收藏"，不需要报 409。可以与第 4 节对照理解。

**没有显式捕获的地方**：

- `message/service.py:28-46` 靠 SELECT 复用已有会话 + `set(participant_ids)` 去重（`:44`），依赖调用方事务，没有 `IntegrityError` 捕获。
- `admin/service.py:132-142` 用 `_seen` 集合去重规避 `permissions.code` 冲突。
- `ai/service.py:780-804` 的 `_upsert_greeting` 用宽泛 `except Exception` 吞掉，缓存路径不影响响应。

### 13.7 注意点与缺口

1. **`oauth_accounts` 没有唯一约束**：`auth/models.py:49-53` 只给 `provider`、`provider_openid` 建了普通索引（`:51-53`）。第三方账号绑定去重仅靠 service 的 SELECT 预检，存在 check-then-insert 竞态窗口——这是唯一索引体系里一个明显的缺口。

2. **唯一索引 ≠ 幂等键**：项目的幂等靠"业务键唯一索引 + CAS"，不是通用请求 ID。`X-Request-ID`（`core/middleware.py:145-147`）只用于链路追踪和 SQL 注释注入（`core/database.py:74-99`），从不用于请求去重；`audit_logs.request_id`（`audit/models.py:56`）只是检索索引。详见第 4 节。

3. **轻量迁移只覆盖 7 个命名唯一索引**：列级 `unique=True`（users/courses/admin 等）不在 `_SQLITE_INDEX_MIGRATIONS` 里，由 `create_all`（新表）和 0001 快照（生产库）负责。历史库升级路径需要对这一点有意识。

4. **Schema 层没有唯一性校验**：`auth/schemas.py:19-24` 的 `RegisterRequest` 只有长度校验，唯一性完全依赖 DB 约束 + service 预检。

### 13.8 一句话总结

> 唯一索引在项目里承担三种角色：**账号标识的唯一性**（用户名/邮箱）、**业务去重**（收藏/评价/举报/申请/成员/会话）、**防一物多卖的最后防线**（`trade_sessions` 部分唯一索引 + CAS 双保险）。它的价值在于把"别重复"这条业务规则下沉到数据库，堵住应用层 `SELECT` 预检与 `INSERT` 之间的并发时间窗。
