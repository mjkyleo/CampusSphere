## P0（3 项）

### P0-1 JWT 签名密钥可带着公开默认值上生产，无任何启动校验
`backend/app/core/config.py:69`、`backend/app/core/config.py:324-361`

```python
secret_key: str = "change-me-to-a-long-random-string-in-prod"
```

`validate_admin_security` 对 Meili/MinIO 密钥做了占位值 fail-fast（`_known_weak` 集合里甚至包含这个 `secret_key` 占位串），但 **`secret_key` 本身从未被检查**——生产启动若 `.env` 漏配 `SECRET_KEY`，系统用公开已知的密钥跑 HS256。攻击者可伪造任意 `{"sub": "<用户ID>", "type": "access"}` 实现全站账号接管（用户 ID 可从需要登录的 `/api/users` 列表枚举）。
**修复**：把 `secret_key` 纳入 `validate_admin_security` 的弱值/长度检查（≥32 随机字符），同样 SystemExit 快速失败。

### P0-2 WebSocket 断线补发无参与者校验——任意登录用户可读取任意会话的私聊历史
`backend/app/modules/message/ws.py:244`（`_compensate` / `_compensate_by_seq`）

```python
if conv:
    if last_seq is not None:
        await _compensate_by_seq(websocket, conv, last_seq)
```

`_authenticate` 只验证 JWT，`conv` 参数从未校验调用者是否为该会话参与者。`/ws?token=<自己的>&conv=<任意会话ID>&last_seq=0` 即可收到最多 500 条缓冲（ZSet）/100 条 DB 记录的他人私聊内容。会话 ID 会通过合法渠道泄露（如 `TradeSessionOut.conversation_id` 返回给买家）。REST 侧的 `get_messages` 有正确的参与者校验，WS 路径漏掉了。*（两个独立审查代理交叉发现，已人工复核）*
**修复**：补偿前查 `Participant(conversation_id=conv, user_id=user_id)`，不存在则拒绝。

### P0-3 ReportModal 违反 Rules of Hooks——打开任意举报弹窗即全站白屏
`frontend/components/ReportModal.tsx:15`，挂载于 `frontend/App.tsx:89`

```tsx
const panelRef = useRef<HTMLDivElement>(null);

if (!reportModal.isOpen) return null;   // ← 早退在 useEffect 之前

useEffect(() => { ... }, [reportModal.isOpen, closeReport]);
```

关闭时渲染 6 个 hook，打开时 7 个 → React 抛 "Rendered more hooks than during the previous render"。且 `ReportModal` 挂在 `ErrorBoundary`（只包 `<Routes>`）**之外**，渲染错误卸载整棵树，直到手动刷新。举报功能（MarketDetail/MessageCenter/CourseDetail 等所有入口）实际上不可用并拖垮全站。
**修复**：把 `useEffect` 移到早退之前，effect 内部用 `if (!reportModal.isOpen) return;` 守卫。

## P1（9 项）

### P1-1 物品审核可被发布者本人绕过
`backend/app/modules/item/service.py:199` + `backend/app/modules/item/statemachine.py:16`

开启审核后新物品为 `PENDING`，只有管理员能通过 `admin/service.py:approve_item` 放行；但状态机允许 `PENDING → ON_SALE`，而 `update_item` 对 owner 调用不做管理员区分——发布者直接 `PATCH /api/items/{id} {"status": 0}` 即可自审上架，还能与管理员审核竞争（先抢先赢）。CAS/权限本身没错，错在转换表对非管理员开放了 `PENDING` 出口。
**修复**：`update_item` 对非管理员拒绝任何离开 `PENDING` 的转换。

### P1-2 存储对象键信任链缺失（三处，同一根因）
涉及 `backend/app/modules/item/schemas.py:86`、`backend/app/modules/share/service.py:47`、`backend/app/modules/storage/router.py:60,47`

1. `ItemImageIn.object_key` / `ShareResource.file_key` 原样入库：任何登录用户可把**任意 key**（包括别人的）挂到自己的物品/资源上；key 还随匿名列表接口公开泄露。
2. `POST /api/files/upload` 接受客户端任意 `key`：可覆盖他人对象（如替换受害者头像/物品图片，uuid key 不可猜但不是秘密）。
3. 预签名直传无 content-length-range / content-type 策略，`prefix` 客户端可控——MinIO 模式下可传任意大小任意内容；share 的 presigned GET 是全站唯一的私桶下载路径，无归属验证。
**修复**：key 模式校验 + 服务端生成 `uploads/{user_id}/{uuid}` 前缀并绑定上传者；presigned PUT 改用带 policy 的 POST。

### P1-3 管理后台封禁按钮状态判断反转
`frontend/pages/AdminDashboard.tsx:1064,1079`

`UserStatus` 枚举是 `Normal=0, Banned=1`（`types.ts:3`），但展示与按钮的三元条件写反：被封号用户显示"正常"、点红色"封禁"按钮实际调用的是**解封** API。管理员在封禁页的每次操作效果都与意图相反。
**修复**：对调 1064-1068 与 1074-1079 两处三元。

### P1-4 修改密码是假成功 stub——根本没有调用后端
`frontend/services/api.ts:1265`

```ts
changePassword: (oldPass: string, newPass: string) => {
  return Promise.resolve({ code: 0, message: '密码修改成功', data: null });
}
```

用户被告知"密码修改成功"，实际什么都没发生。对"认为账号被盗想改密码"的用户是直接的安全伤害。
**修复**：接到真实端点并透出错误。

### P1-5 生产构建保留 mock 回退：后端不可达时所有写操作伪造成功
`frontend/services/api.ts:1183`（`handleMockFallback`）

登录路径已做加固（`AUTH_REAL_PATHS`），但发物品/兼职/资源/评价/组队等其余全部写路径在后端不可达时落回 localStorage mock 并返回 `code: 0`"发布成功"——数据只存在于浏览器。`npm run build` 原样带上。会造成用户数据静默丢失与展示不一致。
**修复**：`import.meta.env.DEV` 门控，生产返回网络错误。

### P1-6 资源分享下载是"假下载"：拿到 URL 后丢弃
`frontend/pages/ShareFeed.tsx:93`

`api.shares.download` 正确取回后端 `{url}`，页面却只弹"正在启动安全下载通道"toast + 本地计数 +1——既不 `window.open` 也不建链。服务端下载计数照加。资源共享模块的核心功能端到端无效。
**修复**：校验 URL 为 http(s) 后 `window.open(url, '_blank', 'noopener')`。

### P1-7 评价去重（2026-09-26 修复）不是并发安全的
`backend/app/modules/course/models.py:29-37`、`backend/app/modules/canteen/models.py:88-96`

9-26 加的 409 去重是纯 SELECT-then-INSERT：两张评价表都没有 `UniqueConstraint(course_id/dish_id, user_id)`，SQLite 索引迁移清单也没有。并发双击/脚本仍可刷出重复评价——恰好是该修复要防的场景。仓库里已有正确范式可抄（`trade_sessions` 部分唯一索引 + `auth/service.py` IntegrityError→409）。
**修复**：加唯一约束（含 SQLite 迁移条目），两个 `add_review` 捕 `IntegrityError` 转 409。

### P1-8 提交在仓库里的占位管理员凭据能通过生产 fail-fast 校验
`backend/app/core/config.py:328` + `config/school.yaml:254,257`

```yaml
password: "change-me-deploy-with-strong-pw-16plus"
key: "change-me-admin-gateway-key-16plus"
```

blocklist 是 `{"", "change-me", "change-me-admin-gateway-key", "change-me-deploy-with-strong-pw"}`——不含带 `-16plus` 后缀的仓库原串（长度还 ≥16）。照模板抄部署的学校会"校验通过"地带着**仓库公开**的管理员网关密钥与 bootstrap 密码上线。`deploy/.env.example` 的 `<GENERATE_RANDOM_16+>` 同样无人拦截（与 `.env.example:21` "所有 <...> 占位会被拒绝启动"的声明不符）。
**修复**：blocklist 加精确串 + `startswith("change-me")` / `<` 前缀模式校验。

### P1-9 自动封禁可被单人操纵
`backend/app/modules/report/router.py:29` + `report/service.py`

`check_auto_ban` 统计该目标的**全部** Report 行（含 REJECTED、含同一举报人重复提交），`submit_report` 无去重、无节流（仅全局 120/min/IP）。5 次请求即可封禁任意用户；且历史驳回举报让"永不超标"——管理员驳回也没用。`target_type` 是自由字符串、`target_id` 不校验存在性。
**修复**：按 distinct 举报人统计 PENDING/RESOLVED；加 `(reporter_id, target_type, target_id)` 唯一约束；`target_type` 收敛为枚举。
