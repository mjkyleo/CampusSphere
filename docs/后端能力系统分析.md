# CampusSphere 后端能力系统分析

> 基于当前工作区实际代码分析（2026-09-10），所有代码位置均指向 `backend/` 下的真实文件。若设计意图无法从代码直接确认，已标注「推断」。

## 0. 整体结论摘要

| 维度 | 内容 |
| --- | --- |
| **项目定位** | 高校校园综合服务平台，服务二手交易、兼职、资料共享、搭子组队、课程/食堂评价与实时沟通等多场景。 |
| **技术栈** | Python 3.12+ / FastAPI（ASGI）/ SQLAlchemy 2.0 异步 ORM / Pydantic v2 / Alembic / Celery（Redis broker）/ Meilisearch / MinIO / Prometheus；配置分层 `.env → school.yaml → AppConfig(DB)`。 |
| **架构形态** | 模块化单体：`app/modules/*` 每域自包含 `router / service / models / schemas`，横切能力下沉到 `app/core/*` 与 `app/tasks/*`。 |
| **核心能力** | ① 配置驱动多校部署；② 声明式 Scope 权限 + 管理员网关隐藏；③ CAS 条件 UPDATE + 部分唯一索引防超卖；④ 预加载/窗口函数去 N+1；⑤ 热点缓存 + Redis 内存降级；⑥ 异步任务（邮件/通知/搜索同步）快速失败降级；⑦ AI 三层降级与内容安全预审；⑧ Prometheus 指标埋点 + 结构化日志 trace id。 |
| **主要风险** | 外部依赖（Meili / AI / MinIO）默认走降级，生产启用前需专项验证；全量测试 >10 min 需分批；部分历史文档仍有漂移，应以源码为准。 |

## 1. 功能清单（按层次/业务域归类）

### 1.1 接口层（Presentation）

| 能力 | 代码位置 | 说明 |

| 模块化路由 | `app/modules/*/router.py`，在 `app/main.py` 装配 | 每个业务域独立 `APIRouter`，前缀 `/api/xxx`。 |

## 2. 设计意图（业务场景 → 核心问题 → 实现思路）

### 2.1 二手交易并发抢占
- **业务场景**：热门闲置物品可能被多个买家同时点击「我想要」。
- **核心问题**：check-then-act 时间窗导致同一物品被卖出多次（超卖）。
- **实现思路**（`modules/item/service.py`）：把「读状态 → 判断 → 写状态」合并为一条带旧状态条件的 UPDATE（CAS），数据库保证只有一个请求 `rowcount=1`；再叠加部分唯一索引与 `IntegrityError` 兜底；状态抢占与会话创建同事务，避免僵尸状态。

### 2.2 热点列表缓存与击穿/雪崩防护
- **业务场景**：物品广场、课程/食堂列表属于高读低写热点。
- **核心问题**：直接查库压力大；缓存穿透（查不存在 key）与同时过期导致雪崩。
- **实现思路**（`core/cache.py`）：namespace 级缓存 + 写操作 `invalidate_namespace` 整体失效；空结果写入 `NULL_SENTINEL` 哨兵防穿透；TTL 加随机抖动防同时过期。

### 2.3 无 Redis / 弱依赖环境下仍可运行
- **业务场景**：本地开发、CI、演示环境可能没有 Redis/Meili/MinIO。
- **核心问题**：强依赖外部中间件会导致“起不来”或“一断就 500”。
- **实现思路**：`core/redis.py` 连接失败进入静默期并回退内存字典（且内存实现与 Redis 语义对齐：TTL、首次自增才 EXPIRE）；`search/client.py` 未启用时静默跳过；`core/storage.py` 降级本地磁盘；AI 不可用时降级规则引擎。

### 2.4 异步任务不拖垮主流程
- **业务场景**：邮件、站内通知、搜索索引同步都是「发完即忘」的副作用。
- **核心问题**：Celery 默认策略在 broker 不可达时会同步重试约 20 次（≈109s），把请求线程卡死。
- **实现思路**：`celery_app` 结果后端 `disabled://` 跳过结果库连接；`broker_connection_max_retries=2` + 1s 超时实现快速失败；调用方统一 `try/except` 包裹 `.delay()`，失败降级（邮件内联直发 / 通知与索引仅记 warning）。

### 2.5 内容安全预审
- **业务场景**：UGC 平台需拦截违规发布内容。
- **核心问题**：AI 审核依赖外部 API，可能因未配 Key、限流或超时不可用；若审核失败就阻断发布，会影响正常用户。
- **实现思路**（`modules/ai/service.py::check_content_safety`）：独立开关 `content.moderation` 控制（**不依赖 AI 总开关**）；开启时优先调 AI 分类，AI 不可用降级 `_rule_moderation` 规则引擎；命中敏感词按配置的 `action`（reject/pending）处置。默认关闭，运营可在后台实时开启。

### 2.6 后台配置无需发版
- **业务场景**：分类、院系分组、食堂维度、邮箱规则、审核开关等运营参数需频繁调整。
- **核心问题**：写死在代码/yaml 里每次调整都要发版。
- **实现思路**：`AppConfig` 表以 `key/value` 存储；读取时「DB 优先，缺省回退 `school.yaml`」；后台 PUT 写 DB 并 `commit` 即实时生效（`get/update_*_config` 系列）；`core/config_reload.py` 支持配置热重载。

### 2.7 管理员入口隐藏与职责分离
- **业务场景**：管理后台是高风险入口。
- **核心问题**：暴露后台路径与接口会扩大攻击面；审计员不应具备写权限。
- **实现思路**：`admin/gateway.py` 网关令牌校验失败返回 **404**（而非 401/403），避免泄露后台存在性；`audit` 作为独立只读 Scope，审计员角色只映射 `audit:view` 与 `user:view`，拿不到 write/admin（职责分离）。

### 2.8 实时消息与断线补偿
- **业务场景**：交易沟通、系统通知需要实时触达。
- **核心问题**：多实例部署下单机 WS 连接无法广播；客户端断线期间消息丢失。
- **实现思路**：`message/ws.py` 通过 Redis Pub/Sub 广播（多实例）；客户端重连带 `since`，服务端用 LocalSeq（Redis ZSet 单调序号）补偿断线期间消息；Redis 不可用时 `redis_subscribe` 返回 `None`，安静降级为单实例推送。

> 说明：2.1–2.8 的实现思路均可从代码直接确认；其中「运营可实时开启预审」「多实例广播」等**业务价值**描述为基于代码结构的合理**推断**。

## 3. 技术取舍（对比维度 → 选择理由）

| 主题 | 候选方案 | 关键维度对比（性能 / 可维护性 / 团队成本 / 生态成熟度 / 扩展性） | 最终选择与理由 |
| --- | --- | --- | --- |
| **架构形态** | 模块化单体 / 微服务 / 传统三层单体 | 微服务扩展性最好但运维与团队成本高；三层单体分层弱、易腐化 | **模块化单体**：按域拆分 `modules/*`，边界清晰、可测试，后续可按域拆服务；当前团队规模下交付与维护成本最低。 |
| **Web 与 ORM 并发模型** | async SQLAlchemy + uvicorn / 同步 ORM + 线程池 | async 在 I/O 密集下吞吐更好，但需要端到端异步（驱动、池、任务）；同步模型简单但高并发线程开销大 | **异步为主**：SQLAlchemy 2.0 async + uvicorn；Celery worker 无事件循环，改用 `sync_db` 同步驱动，避免混用导致阻塞/报错。 |
| **全文搜索** | Meilisearch / Elasticsearch / 数据库 LIKE | ES 功能最强但资源占用与运维重；Meili 轻量、开箱即用；DB LIKE 零依赖但能力弱 | **Meilisearch + SQL LIKE 降级**：有搜索服务时走 Meili；未配置/不可用时降级 `LIKE`，保证任何环境都能搜（正确性优先于相关性）。 |
| **缓存策略** | Redis + 内存降级 / 纯 Redis / 纯本地缓存 | 纯 Redis 强依赖中间件；纯本地缓存多实例不一致 | **Redis + 内存降级**：生产用 Redis（分布式一致），无 Redis 时回退内存字典（本地/CI 零依赖），且内存实现刻意与 Redis 语义对齐（TTL、首次自增 EXPIRE）。 |
| **缓存击穿/雪崩防护** | 空值哨兵 + TTL 抖动 / 布隆过滤器 / 互斥重建锁 | 布隆过滤器最省内存但实现与维护复杂；互斥锁逻辑重且可能死锁 | **空值哨兵 + TTL 抖动**：实现简单、无额外组件，足以覆盖校园场景的量级与风险；复杂度可控。 |
| **限流算法** | 固定窗口（Redis Lua） / 滑动窗口 / 令牌桶 | 固定窗口实现最简单、语义清晰，但窗口边界可能两倍突发；令牌桶最平滑但实现与调参成本高 | **固定窗口 + Lua 原子自增**：用 Lua 保证「INCR + 首次 EXPIRE」原子；认证端点独立限流。已知局限（边界突发）在校园业务量级下可接受。 |
| **防超卖并发控制** | CAS 条件 UPDATE + 唯一索引 / 分布式锁 / 悲观锁 / 乐观锁版本号 | 分布式锁需额外组件且有死锁/超时问题；悲观锁降低吞吐；版本号需额外字段与重试 | **CAS 条件 UPDATE + 部分唯一索引**：一条 SQL 完成判断+写入，数据库保证原子；无额外组件、无死锁；唯一索引兜底极端不一致。 |
| **任务队列** | Celery / RQ / Arq / 自研 | Celery 生态最成熟（路由、重试、监控、beat），但重；RQ/Arq 轻量但功能少 | **Celery**：路由（email/notify/search）、acks_late、指数退避重试开箱即用；配合 `backend="disabled://"` 与快速失败，规避其“重”的副作用。 |
| **AI 集成方式** | OpenAI 兼容协议 + 三层降级 / 直连单一厂商 SDK / 无降级 | 直连 SDK 切换供应商成本高；无降级会在 AI 故障时拖垮发布流程 | **OpenAI 兼容协议 + 三层降级**：协议标准化便于换供应商/自建网关；总开关→能力级→模型链+熔断，逐层降级到规则引擎，保证 AI 永远不是发布链路的单点故障。 |
| **配置管理** | DB 覆盖 + 热重载 / 仅 yaml / 配置中心（Nacos 等） | 仅 yaml 改配置要发版；配置中心能力全但引入新组件与运维 | **DB(AppConfig) 覆盖 + 热重载**：复用现有数据库，运营改配置实时生效；`school.yaml` 作为多校基线，`.env` 覆盖密钥等环境差异。 |
| **对象存储** | storage_client 抽象 + 本地降级 / 直连 MinIO SDK / 直连云厂商 SDK | 直连 SDK 会导致环境无法起、供应商锁定 | **抽象 + 本地磁盘降级**：未配置 MinIO 时落本地磁盘；接口稳定，后续换供应商只改实现。 |
| **实时消息** | Redis Pub/Sub + LocalSeq 补偿 / 短轮询 / 单实例 WS | 短轮询实时性差且浪费；单实例 WS 无法多实例广播 | **Redis Pub/Sub 广播 + LocalSeq 断线补偿**：多实例可达；`since` + ZSet 单调序号保证断线不丢不重；Redis 不可用时安静降级。 |

## 4. 简历可用亮点（后端开发岗位）

> 以下 5 条均对应本仓库**可验证的真实实现**，突出「解决什么问题 + 用了什么方法 + 达到什么效果」，避免堆砌名词。

1. **设计二手交易并发抢占方案，根治超卖**：用带状态条件的 UPDATE（CAS）把「读-判断-写」合并为原子操作，配合部分唯一索引兜底与事务边界收敛，解决同一物品被并发下单重复卖出的问题；状态抢占与会话创建同事务，避免产生无会话的僵尸状态。
2. **治理列表/详情 N+1，将查询从 O(3N+1) 压缩到 4 条 SQL**：通过 `selectinload` 预加载关联图片、用窗口函数一次性聚合会话未读数与最新消息，显著降低列表接口数据库往返；热点列表再叠加 namespace 缓存与空值哨兵，防穿透同时避免雪崩。
3. **构建「外部依赖可降级」的高可用运行时**：Redis、Meilisearch、MinIO、AI 均提供降级路径——Redis 不可用时回退内存实现且语义对齐（TTL/首次自增 EXPIRE），搜索引擎未启用时降级 SQL LIKE，AI 不可用时降级规则引擎；保证无中间件的本地/CI 环境仍可完整启动与测试。
4. **打通异步任务链路并保证不拖垮主流程**：为邮件、站内通知、搜索索引同步设计 Celery 任务与队列路由；通过结果后端禁用 + broker 快速失败 + 调用方 `try/except`，把 broker 不可达的影响从「卡死请求线程约 2 分钟」降级为「内联直发或仅记日志」，并补齐 Prometheus 请求计数/延迟埋点使告警真正生效。
5. **AI 能力工程化：三层降级与内容安全预审**：封装 OpenAI 兼容协议客户端，实现「总开关 → 能力级开关 → 模型链+熔断」三层降级；在资料共享、组队、兼职发布路径接入统一内容安全预审（`check_content_safety`），AI 不可用时自动降级敏感词规则引擎，保证审核能力不中断、也不阻断正常发布。

> 备选亮点：**管理员网关 404 隐藏 + 短时令牌**（降低后台暴露面）、**配置分层（DB 覆盖 + 热重载）**（运营改配置零发版）、**WebSocket 多实例广播 + LocalSeq 断线补偿**（实时消息不丢不重）。
